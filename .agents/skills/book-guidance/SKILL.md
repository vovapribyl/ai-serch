# Выбор инженерных правил

Проверь [статус пайплайна](../../../docs/book-guidance-pipeline.md#статус). Пока результат не утверждён владельцем, библиотеку можно обсуждать и проверять в рамках подготовки этого пакета; автоматически применять её как нормативный процесс к последующей разработке нельзя.

## Выбор

Сначала определи результат задачи, ограничения и существующее устройство затронутого кода. Книжные правила не заменяют предметные требования и не расширяют scope. Если отдельного инженерного вопроса нет, дополнительные правила не загружай; механические правки проходят без этого skill.

Выбери основной набор по проблеме, а не по наличию слова «API» или «модель». Прочитай только соответствующий `mini` перед проектным решением:

| Вопрос | Основной набор |
|---|---|
| Глубина модуля, скрытие деталей, разбиение, публичный контракт | [A Philosophy of Software Design](references/upstream/a-philosophy-of-software-design/a-philosophy-of-software-design.mini.md) |
| Зависимости бизнес-логики от БД, framework, файлов, сети или ML-адаптера | [Clean Architecture](references/upstream/clean-architecture/clean-architecture.mini.md) |
| Локальная читаемость, имена, побочные эффекты, обработка ошибок | [Clean Code](references/upstream/clean-code/clean-code.mini.md) |
| Предметные понятия, язык, инварианты и жизненные циклы | [Domain-Driven Design](references/upstream/domain-driven-design/domain-driven-design.mini.md) |
| Реализация определённой предметной модели: агрегаты, транзакции, события, переводы между контекстами | [Implementing DDD](references/upstream/implementing-domain-driven-design/implementing-domain-driven-design.mini.md) |

Один основной набор — отправная точка, а не числовой лимит. Дополнительный подключай только для другого конкретного вопроса и обозначай, какие решения он регулирует. APoSD и Clean Code не применяй как равноправные требования к разбиению: APoSD регулирует границы модулей/API, Clean Code — локальную читаемость. Для DDD и Implementing DDD обычно выбери один по уровню задачи. Не вводи агрегаты, события или дополнительные слои только из-за их наличия в источнике.

Если `mini` недостаточно, найди нужный раздел одноимённого `full` без суффикса `.mini` в той же папке. Не читай все `full` подряд. [Сопоставление APoSD и Clean Code](references/upstream/docs/compatibility/a-philosophy-of-software-design/clean-code.md) открывай только при спорном совмещении; его процентные оценки — суждения автора, не измерения эффективности проекта.

## Применение

- Требования, безопасность и действующие решения проекта имеют приоритет над рекомендациями источника, включая заголовки `OBEY`. Книга не разрешает новый scope, runtime-запуск, изменение зависимостей или переход контрольной точки.
- Для существенного выбора кратко свяжи наблюдаемую проблему с выбранным принципом и способом проверки. Не создавай отдельный отчёт или план-контракт для каждого применения: процесс определяется маршрутом задачи.
- Проектирование завершается требуемым контрактом, вариантами и проверкой ограничений; реализация — требуемым поведением и релевантными проверками. Размер diff и «соответствие книге» не являются критериями приёмки.
- Ponytail не перенастраивай. Если он применён, при конфликте с выбранным правилом сохраняй требования, защитные проверки и обоснованные границы; обосновывай выбор задачей, а не числом строк.
- В обычной записи [журнала](../../../docs/task-quality-journal.md) указывай реально прочитанные наборы, уровень `mini/full`, версию источника и конкретное применение либо «не применялись». Не приписывай им результат без evidence и не выполняй задачу повторно для сравнения.

Оригиналы источника сохранены без изменения языка и текста. Commit и SHA-256 находятся в [source-manifest.json](source-manifest.json), лицензия — [LICENSE](LICENSE). Полные копии служат справочником, а не дополнительными активными skills.
