# Поиск ранее рассмотренных товаров и вариантов

Проект внутренней системы, которая помогает сотруднику найти ранее рассмотренный
товар по фотографии и доступным данным карточки. Один товар может встречаться
у разных продавцов, на разных площадках и под разными ссылками. Поиск должен
возвращать накопленную информацию о товаре, а окончательное решение оставлять человеку.

В репозитории собраны анализ предметной области, требования, архитектура, реализация и отчёты проверок. Этот README описывает систему в целом. Подробности отдельных работ вынесены
в соответствующие документы.

## Какую задачу решаем

Сейчас команда проверяет повтор товаров по ссылкам-исходникам из каталогов продавцов, маркетплейсов и других источников. Со временем ссылки протухают: не открываются, товар в карточке меняется и другие проблемы. Визуально сравнение по фото и память сотрудников тоже не дают надёжной связи с историей рассмотрений.

Целевой сценарий системы:

1. Сотрудник загружает фотографию товара и передаёт доступные сведения о нём.
2. Система ищет кандидатов в товарной базе и формирует топ похожих моделей.
3. Сотрудник изучает кандидатов, доступную историю и статусы найденных записей.
4. Человек определяет, найден тот же товар, его вариант или другая позиция.

Это видение продукта, а не утверждение о готовности всех возможностей.
В исходном MVP пользователь `CHECK` просматривает результат и не создаёт
или изменяет товарные записи. Границы описаны в [Vision & Scope](docs/analysis/01-vision-and-scope.md).

## Как устроен поиск

Предметная цель — поиск товаров. Текущий экспериментальный сценарий проверяет
её на накладных ногтях: сравниваются отдельные области, а не только целое фото.
Применимость этого способа к другим категориям пока не подтверждена.

1. Изображение поступает в **локализатор товара**: он находит предполагаемые области
   ногтей и возвращает маски. В его основе — Grounding DINO и SAM через LangSAM.
2. Код обработки по маскам создаёт кропы: обрезает область и заменяет фон
   за пределами маски белым. Для запроса и каталога используется одинаковое правило.
3. Три модели независимо преобразуют каждый кроп в числовой вектор — embedding.
4. Код поиска вычисляет косинусное сходство векторов, сопоставляет области
   запроса и фото каталога и ранжирует товары.

| Компонент | Роль | Результат |
|---|---|---|
| Локализатор | Находит области ногтей | Маски и координаты; кропы создаёт код обработки |
| OpenCLIP | Преобразует кроп в embedding | Вектор из 512 чисел |
| DINOv2 | Преобразует кроп в embedding | Вектор из 768 чисел |
| SigLIP2 | Преобразует кроп в embedding | Вектор из 768 чисел |
| Алгоритм сравнения | Сопоставляет векторы и области | Баллы сходства и порядок кандидатов |

Векторы каталога сохраняются заранее. При поиске рассчитываются векторы нового
запроса; каталог не нужно пересчитывать для каждого поиска. Модели embeddings
сами не выбирают товар. Балл сходства не является вероятностью совпадения.

## Как устроено пополнение базы товаров

Первоначальный импорт и последующее пополнение — разные процессы.
Исторический Gate 2 подтвердил загрузку 674 записей из согласованного XLSX.
Это не означает, что для всех этих записей уже рассчитан и проверен новый
поиск по отдельным областям.

Для последующего пополнения реализованы:

- Обработка до пяти выбранных фото за запуск. Состояния и checkpoints — сохранённые
  результаты стадий — хранятся в PostgreSQL; маски, кропы и файлы векторов — отдельно.
- Раздельная обработка: локализация → сохранение областей → завершение процесса
  локализатора → последовательный расчёт embeddings, одна модель за раз.
- Публикация товара через снимок каталога после завершения всех выбранных фото
  этого товара, если хотя бы одно фото обработано успешно.
- RESUME и явные команды повтора ошибочного фото или публикации с переиспользованием
  готовых результатов. Автоматического повтора ошибок нет.
- Работа поиска и пополнения по очереди, проверка нагрузки, свежести измерений
  и сроков выполнения. При недостоверном наблюдении обработка останавливается.
- Журналы операций и терминальный монитор: прогресс, стадия, длительность,
  измерения ресурсов и первая сохранённая причина остановки.

Этот процесс проверялся в изолированных тестовых контурах. Переключение нового
каталога в рабочий поиск и откат остаются отдельными задачами.

## Локальная разработка

Основной стек: Python 3.12, FastAPI, PostgreSQL с pgvector, Alembic, Pillow
и PyTorch. Зависимости приложения описаны в [pyproject.toml](pyproject.toml),
команды разработки — в [Makefile](Makefile). Проверяемая программная логика
разрабатывается по TDD; используются pytest и Ruff.

При подготовленном окружении пример проверки без ML и БД:

```sh
PYTHONPATH=src:. .venv/bin/python -m pytest tests/test_replenishment_waiting.py
```

ML-пробы выполнялись локально на macOS с MPS, в отдельно подготовленных
окружениях с локальными весами. Установка базового пакета не подготавливает
весь ML-runtime. Runtime-параметры и секреты хранятся вне репозитория;
[.env.example](.env.example) содержит шаблон настроек. Веса, исходные фото,
приватные данные и подробные runtime-артефакты в Git не входят.

Для реального запуска нужны выбранные входы, отдельный тестовый контур и
проверенный пакет исполнения. Порядок, команды и ограничения приведены
в [инструкции проверок](specs/001-corpus-replenishment/quickstart.md). Она не означает, что базовый Web уже поддерживает весь поисковый сценарий.

## Ближайшие шаги

1. Проверить области неудачного запроса и ожидаемого фото каталога.
2. Завершить два оставшихся запроса на коде с исправленной телеметрией, сохранив уже полученные результаты.
3. После оценки качества подготовить следующую конечную проверку на 50–100 фото.
4. Отдельно проверить подключение нового каталога к пользовательскому поиску и откат.
