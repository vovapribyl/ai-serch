# G2 — пакет решений для подготовки фото и сравнения

Дата: 2026-10-07. Статус: **APPROVED_BY_OWNER**.

Это ограниченный пакет для US2/T020–T031 из [tasks](tasks.md), а не утверждение всего HLD/LLD. Основание: [LLD §4–8](../../docs/architecture/nail-search-lld.md#4-внутренние-контракты), [утверждённый HTTP-контракт](../../docs/architecture/candidate-i-http-contract.md). Принятые владельцем правила поиска сохраняются.

## План-контракт

Маршрут FULL: выделить уже предложенные детали G2 → проверить согласованность с HTTP и правилами владельца → независимое read-only review → исправить существенные замечания → предъявить владельцу. До утверждения пакета зависимая реализация US2 не начинается. Код, зависимости, модели, БД и корпус эта подготовка не меняет.

Book-guidance: Clean Architecture mini, commit `893a88a6fce3a80c565bf39ac65021b43a8b2990`; файлы/декодирование и ML остаются в адаптерах, crop/сопоставление/ranking — в ядре. Ponytail full: стандартная библиотека для matcher, существующие providers через адаптер, без нового solver-пакета или универсального plugin registry.

## Что предлагается принять

| Область | Точное правило | Зачем и простой пример |
|---|---|---|
| Декодирование | Проверить SHA-256 исходных bytes; применить EXIF orientation, затем получить RGB8; прозрачность составить поверх белого. Размеры и маски относятся к этому нормализованному кадру | Фото телефона будет правильно повёрнуто до выделения. Полностью прозрачный пиксель станет белым |
| Порядок областей | Профиль задаёт `(-confidence,x0,y0,x1,y1,label)`; точные дубликаты сохраняют исходный порядок. HTTP ordinal 1..N следует этому порядку; confidence не фильтрует области | Повторная обработка сохраняет адреса областей и устойчивый порядок. Это правило уже закреплено ссылкой в HTTP-контракте |
| Crop | Минимальный прямоугольник ненулевых пикселей маски: `(min_x,min_y,max_x+1,max_y+1)`, padding 0, без поворота/сглаживания. Вне маски RGB `(255,255,255)`. Сохранить detector box и отдельный crop box | Пиксели маски с X=2..4 и Y=1..3 дают box `(2,1,5,4)` и crop 3×3. Правая/нижняя границы не включаются |
| Query/catalog | Один профиль подготовки и модели с теми же revisions/processor identities. Query crops в памяти; каталожные производные — PNG без EXIF/lossy compression через файловый адаптер | Одинаковое изображение не получает разные правила подготовки в двух путях |
| Численная подготовка | Обе стороны привести к float32; затем cosine считать в float64 после L2-нормализации. Reject non-finite/zero-norm, неверные размеры и неполный набор моделей | Каталожные и query векторы сравниваются с одинаковой исходной точностью. Полный набор: `openclip_b32` 512, `dinov2_b14` 768, `siglip2_b16_224` 768 |
| Шкала пары | `c = clamp(cosine,-1,1)`, `s=(c+1)/2`; `S` — среднее `s` трёх моделей. Порог отбрасывания пар отсутствует | Cosine −1 → 0, 0 → 0.5, 1 → 1. Это относительная оценка, не вероятность совпадения товара |
| Assignment | Одна общая оптимальная assignment по `S`, ровно `min(n,m)` реальных пар, без повторного использования. Остальные query области дают 0; итог делится на `n` | Уже принятое правило: три query области, две пары 0.9 и 0.6 → `(0.9+0.6+0)/3=0.5` |
| Solver | Точный `subset_dp_v1` по меньшему набору, стандартная библиотека; не greedy. Превышение обязательного конечного бюджета → `RESOURCE_LIMIT`, без обрезания областей или скрытого fallback | Для `[[0.90,0.80],[0.85,0.10]]` выбрать перекрёстные пары: `(0.80+0.85)/2=0.825`; greedy получил бы 0.5 |
| Равенство assignment | Сравнить рассчитанные float64 суммы; при точном равенстве выбрать лексикографически меньшие назначения в query order, реальные catalog ordinals раньше null. Не добавлять epsilon. Допуск в сравнении с независимым oracle — `1e-12`, не правило выбора пар | При одинаковых оценках выдача остаётся воспроизводимой; округление UI не участвует в выборе |
| Ranking | Лучший score пары фото на товар. Равенство внутри товара: меньший query ordinal, затем catalog ordinal. Между товарами: `(-score,product_record_id)`. До 10 уникальных товаров | Дополнительные фото не дают бонуса. Если товаров меньше десяти, выдача короче |

Файловая граница остаётся `NailImageStorePort`: opaque internal references внутри validated private root, проверка checksum, отсутствие выхода через symlink, права/владение производными и cleanup. Ядро получает только immutable plain DTO из LLD §4; пути, Pillow, HTTPX, tensors и ORM в ядро не передаются. US2 добавляет только необходимые ему image/embedding/read-catalog операции; build/publish/evaluation детали здесь не утверждаются.

`NO_NAILS` и техническая ошибка остаются разными исходами. Ошибка одной области отклоняет фото целиком. Нет фильтра качества, whole-image fallback или автоматического «товара нет»; решение после просмотра кандидатов принимает владелец.

## Что это разрешит и что остаётся отложено

Утверждение этого пакета разрешит немодельную реализацию и синтетические проверки T020–T031 в существующем изолированном worktree: image-store, общий processor, matcher, fake embedding facade и ranking use case. Минимальные DTO/порты реализуются по LLD §4 только для этих сценариев.

Конечные pixel/region/solver/memory limits и deadlines обязательны, но их рабочие значения остаются **UNKNOWN** до отдельной ресурсной проверки. В синтетических тестах задаются явные конечные параметры; они не становятся production defaults. При отсутствии обязательных параметров реальный запуск запрещён. Принятие алгоритма DP не доказывает его пригодность для реального числа областей на Mac.

**DEFERRED:** физическая schema и её constraints, build/coverage/publication, Web/session/evidence integration, реальные revisions/bills/locks/runtime values, real I bootstrap и inference, corpus/manual quality acceptance. Gates G1/G3/G4/G5 сохраняются. Sheets, VM/internet, другие категории, пользователи/auth и Candidate J остаются backlog.

Это проверки примеров документа, не GREEN нового matcher или проверка ML-качества. Состояние code worktree/ledger подтверждает завершённые T001–T019; US2 ещё не реализован.
