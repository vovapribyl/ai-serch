# Предложение по снижению расхода памяти

2026-10-11. STANDARD, DRAFT_PROPOSAL: анализ и варианты, без изменения кода,
профиля, лимитов или нового ML-прогона. Основание: владелец после ручного поиска
сообщил «Ищет отлично» и попросил предложить решение ресурсной проблемы.
Это положительная оценка проверенных примеров; число запросов, полнота проверки20
и формальные оценки UNKNOWN. Не означает качество всего100 или закрытие T051.

## Наблюдаемая ситуация

[Диагностика](memory-pressure-diagnosis.md) установила системный critical pressure4
на Mac с16GiB RAM; processRSS ceilings не превышены. Metal/MPS footprint не измерен,
виновник конкретной остановки UNKNOWN. Гипотеза совместной нагрузки ML и host
остаётся UNVERIFIED. Новые наблюдения ниже — статические, не замена профилированию.

Код проверен в worktree candidate-i-http:

- `nail_native_bindings.native_factories`: все embedding providers на MPS;
  `NailEmbeddingAdapter.encode`: каждый provider лениво загружается и остаётся
  в `providers`. Lease сериализует вызовы, но не ограничивает резидентные модели.
- `TransformersImageProvider`: полный `AutoModel` переносится на device;
  при вычислении выбирается только `vision_model`. Для SigLIP2 текстовая ветвь
  присутствует в весах, но в текущем image-only пути не используется.
- `OpenClipImageProvider`: полный CLIP загружается, вызывается только `encode_image`.
- Оба embedding providers уже используют `eval()` и `torch.inference_mode()`;
  добавление этих режимов не является новым решением.
- `NailCatalogBuildService` обрабатывает одно фото: localize → три encoder →
  сохранение результата. Следующее фото снова localize; I остаётся отдельным процессом.
  `NailSearchService` также обрабатывает каждое query photo через все три encoder.

## Конкретный резерв в весах

Read-only чтение только заголовков safetensors выбранных файлов, без Torch,
загрузки тензоров или inference. В OpenCLIP учтён именно
`open_clip_model.safetensors`, который использует loader; альтернативный
`model.safetensors` не суммируется, чтобы не завысить расход.

| Модель | Image/auxiliary payload, MiB | Неиспользуемая текстовая часть, MiB |
|---|---:|---:|
| OpenCLIP B32 |335,12|241,96|
| DINOv2 B14 |330,28|0|
| SigLIP2 B16/224 |354,33|1076,90|
| Итого |1019,73|1318,86|

Это payload параметров, преимущественно F32; total2338,58MiB. Потенциальное
сокращение неиспользуемых весов≈1,288GiB. Не измерение RAM/GPU и не обещание
такой же экономии физического footprint: есть buffers, activations, cache,
frameworks, временные копии при load и другие процессы. Округления возможны.

Векторы сами по себе малы: при100фото×10областей×(512+768+768)×4bytes —
7,8125MiB плотных float32. Python/JSON/SQL overhead сюда не входит. Уменьшение
числа фото не уменьшает постоянный размер загруженных моделей; влияет на число
вызовов, артефакты и возможное накопление памяти.

## Приоритетный вариант

Сохранить три image encoder, веса, preprocess, pooling/projection, float32,
нормализацию и ranking. Изменить только способ загрузки и время жизни моделей.

1. Добавить stage/model telemetry в уже работающие ML-процессы: время load/encode,
   live tensor bytes, Metal driver bytes, host pressure/compressor/swap.
   Не импортировать SDK в отдельный observer. Не складывать live и driver bytes:
   driver уже включает allocator pools и MPS/MPSGraph.
2. Начать с vision-only SigLIP2; затем удалить ненужную текстовую ветвь OpenCLIP.
   Желательно не создавать текстовые тензоры даже временно при загрузке.
   Не создавать случайный encoder из одного config: использовать исходные веса.
   Требуется сравнение embeddings и выдачи с текущим accepted способом.
3. После завершения вызовов освобождать временные tensors; очищать свободный MPS
   cache на подходящих границах только по измерениям. `empty_cache()` освобождает
   неиспользуемый cache, не живые веса. Постоянная очистка после каждого crop может
   увеличить задержку; сама по себе не заменяет управление lifetime.
4. Если пиковая нагрузка всё ещё чрезмерна, разделить сборку корпуса на стадии:
   localize → сохранить mask/crop → завершить own I process; затем encoder A для
   всех сохранённых crops → завершить worker; аналогично B и C → собрать индекс.
   Читать crops с диска ограниченно, не держать весь corpus в RAM. Один worker
   на стадию, не новый процесс на каждый crop. Завершение own worker освобождает
   его процессные ресурсы надёжнее, чем надежда на удаление одной Python-ссылки.

Стадийная сборка требует отдельного checkpoint промежуточных результатов,
проверки hashes/profile и атомарного признака полноты всех3models. Текущая БД
не должна помечать фото OK после одной модели; публикация остаётся отдельной.
Ошибки отдельных фото и глобальный pressureSTOP сохраняют разные политики.
Это изменение build orchestration, а не небольшая правка существующего adapter.

Для интерактивного поиска сначала оставить три облегчённых image providers
загруженными: повторная загрузка всех моделей на каждый запрос замедлит UI.
Если этого недостаточно — отдельно выбирать между sequential worker lifecycle
(экономнее, медленнее) и выделенным ML-host (быстрее для пользователя, сложнее
эксплуатация). Поиск и build не должны требовать одинакового режима residency.

## Альтернативы и ограничения

| Вариант | Возможный эффект | Ограничение / место в очереди |
|---|---|---|
| Только image части тех же моделей |Меньше постоянных весов без намеренной смены алгоритма|Первый кандидат; эквивалентность ещё не проверена|
| Поэтапная сборка с завершением workers |Меньше одновременной residency и накопления в долгом процессе|Следующий вариант; новый build checkpoint, дополнительные load/I/O|
| Одна/две embedding модели вместо трёх |Меньше вычислений и весов|Меняет score/model contract; качество проверить на owner примерах. DINO/SigLIP/OpenCLIP заранее победителем не назначать|
| float16/quantization |Меньше bytes части tensors/weights|Не означает половину общейRAM; совместимостьMPS/SDK и качество UNKNOWN, новыйruntime/indexprofile|
| CPU для embedding |Меньше Metal allocations|CPU использует ту же физическуюRAM, возможна меньшая скорость; не гарантирует уменьшение footprint|
| Отдельный ML-host |ИзоляцияMLнагрузки от рабочего Mac|Выборhost/стоимости/развёртывания отдельно; no purchase/publication here|

Для исследования одной/двух моделей можно пересчитать комбинации scores по уже
сохранённым vectors корпуса без повторной catalog localization. Для реальных
WB-query нужны их embeddings всех3models: наличие только финальной выдачи/меток
не гарантирует их сохранение. Замена encoder, dtype, preprocessing требует
проверки совместимости либо новой версии полного index, без смешивания векторов.

## Предлагаемая проверка перед большим корпусом

Подготовить один небольшой frozen набор owner queries с ожидаемыми товарами и
сложными отрицательными примерами. Размер согласовать по доступным сохранённым
данным, не объявлять всю20проверку завершённой. Сначала проверить bounded telemetry
и image-only вариант на этом наборе: сравнить vectors, top10/rank expected product,
labels владельца, время первого/повторного запросов, память до/после и её рост.

Успех: качество владельца сохранено; старые resourceSTOP не срабатывают в
согласованном окне; память возвращается к стабильному уровню после warmup.
Точный memorybudget/число повторов фиксировать до пробы. СнижениеRAM не обещать
до измерений. Затем проверять длительную сборку с checkpoints и восстановлением,
после неё оставшиеся78PENDING. Малый тест не доказывает стабильность всей100.

Все implementation/ML windows отдельно; текущий manual20runtime не редактировался.
Процессные boundaries/lifetime/telemetry остаются во внешнем runtime/adapter;
изменения build стадии должны сохранять plain domain invariants и completeness.
Применён Clean Architecture mini, upstream commit893a88a6..., без causalclaim.

## Первичные внешние источники

- [PyTorch driver_allocated_memory](https://docs.pytorch.org/docs/2.14/generated/torch.mps.driver_allocated_memory.html): total Metal allocations, cache/framework включены.
- [PyTorch empty_cache](https://docs.pytorch.org/docs/2.14/generated/torch.mps.empty_cache.html): только неиспользуемый allocator cache.
- [Transformers SigLIP2](https://huggingface.co/docs/transformers/model_doc/siglip2#siglip2visionmodel): отдельный vision model и image-only interface; совместимость конкретного pinned SDK ещё проверить.
