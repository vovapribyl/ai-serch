# Лёгкий мониторинг пополнения в терминале

Дата: 2026-10-14. Статус: реализовано; проверено на synthetic данных, сохранённом результате и во время реальной партии из пяти фото. [Результат runtime-проверки](monitor-runtime-report.md).

Владелец выбрал терминальную сводку без нового сервера. Она обновляется раз в3секунды и только читает приватные свидетельства. БД, модели, поиск и управление worker-процессами монитор не запускает.

## Что показывает

- Последнее известное состояние партии; подтверждённый итог или UNKNOWN.
- Число выбранных фото, фото с терминальным исходом и фото с исходом OK. NO_NAILS/ERROR учитываются как получившие исход, но не как OK.
- Число подтверждённых checkpoint и успешных публикаций.
- Последнюю стадию и модель, длительность партии и стадии. Длительность стадии останавливается на записи выхода worker; она включает подготовку и ожидание, не только inference.
- Возраст последнего ресурсного наблюдения, его статус и RSS/MPS. Старые значения явно помечаются как устаревшие, свежесть берётся из замороженного package.
- Полноту доступной истории и зарегистрированную ошибку без её приватного сообщения.

Во время выполнения controller ведёт обычную обработку, а отдельный reader читает файлы. Это обходит последовательное обслуживание START текущим owner socket без изменения командного протокола.

Для будущих запусков controller-журнал дополнен агрегатами: total_photos при START, события после подтверждённого finish_photo и безопасные счётчики/причина из итоговой SQL-сводки. Исходные ID, пути фото, vectors и содержимое ошибок не добавляются. Источник истины для состояний остаётся БД; reader не меняет состояние и не предлагает resume по одному журналу.

## Запуск

Из корня репозитория:

```bash
.venv/bin/python -B scripts/monitor_replenishment.py --runtime-root /absolute/private/package-directory --watch
```

`--runtime-root` указывает на приватный каталог пакета с runtime-binding.json и ресурсным журналом, а не на вложенный shared_runtime_root. Без `--watch` команда показывает один снимок. `--interval` задаёт период чтения от1до60секунд, по умолчанию3. `--seconds` ограничивает наблюдение от1до3600секунд, по умолчанию1200.

При наличии записи закрытия host наблюдение заканчивается. Ctrl+C останавливает только viewer. Оно не останавливает controller и не отменяет партию. В обычном терминале экран обновляется; при перенаправлении вывода сохраняются последовательные снимки.

Для текущего локального эксперимента путь можно взять из приватного указателя:

```bash
.venv/bin/python -B scripts/monitor_replenishment.py --runtime-root "$(cat /tmp/replenishment-049-current-root.txt)" --watch
```

Этот указатель относится к экспериментальным пакетам и не является механизмом поиска активного production-процесса.

## Доказательность и ограничения

Viewer проверяет права каталогов700 и файлов600, владельца, отсутствие symlink для читаемого файла и ограниченный размер. Он читает до трёх файлов событий по1MiB и только хвост resource-observations.jsonl до8KiB. Недописанная последняя строка пропускается до следующего обновления. Разрыв sequence после ротации или неполный итоговый status означает неполную историю; checkpoint-счётчик в таком случае UNKNOWN.

Старые журналы не содержали итоговой причины партии и отдельных событий исходов фото. Для сохранённых experimental runs viewer может использовать probe050-result.json при совпадении package SHA. Без этой итоговой сводки успешное возвращение старого batch wrapper само по себе не объявляется COMPLETED. Отсутствующие итоги не превращаются в нули.

Старый heartbeat не доказывает зависание или гибель controller. Для завершённой партии его возраст естественно растёт. Отсутствие нового checkpoint также не является диагнозом зависания inference. CPU в эту минимальную сводку не добавлен: постоянный resource guard не содержит такого измерения; новые опросы ОС/GPU ради viewer не выполняются.

Пока нет внешних уведомлений, фоновой службы, веб-интерфейса, автоматического restart/retry или диагностики причины смерти controller. Viewer показывает проблему с данными наблюдения, но не назначает ей причину. Собственная стоимость чтения файлов и дополнительные записи агрегатов в ML-партии не измерены.

## Проверка

TDD проверяет привязку прогресса к checkpoint/подтверждённым исходам фото, правильные длительности и итог, неизвестный legacy результат, устаревшие ресурсные данные, неполную строку и историю, права доступа, отсутствие raw aliases в выводе и watch-обновление с завершением. Logger-тест проверяет агрегаты без приватных полей, сохранение аргументов и результата.

На сохранённой успешной партии19ad687c реальный CLI показал COMPLETED,5/5фото с итогом,5OK,20checkpoint и5публикаций; heartbeat отмечен устаревшим. Это проверка чтения исторического результата, не новый модельный запуск. Итоговая регрессия:163selected tests PASS30,77с, один существующий Starlette/httpx warning. Ruff/format/diff прошли. Проверки host/logger/supervisor используют synthetic процессы без ML/БД.

После изменений runtime-кода прежний consumed пакет не соответствует текущему коду. Для проверки мониторинга во время реальной партии нужна новая заморозка и отдельное разрешение по [quickstart](quickstart.md). Read-only просмотр существующих приватных результатов такого гранта не требует.
