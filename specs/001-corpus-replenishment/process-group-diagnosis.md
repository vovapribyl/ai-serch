# Отказ проверки группы процессов: диагностика и исправление

Дата: 2026-10-14. Статус: **SYNTHETIC_VERIFIED**. Модели и БД не запускались.

Основание: владелец разрешил выяснить отказ ОС из [пробы журнала](operation-log-probe-report.md). Работа выполнена в текущей ветке codex/upload-optimiz. Проверены собственные короткие процессы; сигналов чужим группам не отправляли.

## Что нашли

На этой macOS `os.killpg(pgid, 0)` может вернуть `EPERM` для группы, в которой остались только zombie-процессы. Zombie уже завершился, но родитель ещё не забрал его статус. После удаления группы тот же вызов возвращает `ESRCH`.

Наш registry предполагал только два исхода: группа существует или отсутствует. `PermissionError` выходил наружу и прерывал обработку, хотя группа могла исчезнуть спустя короткое время. Это дефект обработки результата проверки ОС, а не установленная ошибка нейросети.

В [исходнике Apple XNU, killpg1](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c) фильтр группы исключает SZOMB, а отсутствие подходящих участников при существующей группе может дать EPERM. Код main объясняет возможный механизм; он не является доказательством точной версии установленного ядра. Локальные эксперименты ниже подтвердили само поведение на этой машине.

## Проверки гипотезы

| Сценарий | Наблюдение |
|---|---|
| Обычный отдельный процесс, три реальных Python-окружения | По30случаев: живая группа видна; после wait/reap по90проверок группы и PID возвращают ESRCH. EPERM не воспроизведён |
| Завершившийся, ещё не забранный родителем лидер | 10из10случаев: ps подтверждает zombie, проверка группы даёт EPERM, проверка PID доступна. После wait/reap — ESRCH |
| Worker+guardian без задержки | 40случаев: сразу после reap лидера ESRCH; отказ не воспроизведён |
| Guardian завершает TERM на12мс позже лидера | 40случаев; наблюдалась последовательность PRESENT→EPERM→ESRCH.105проверок вернули EPERM; все группы исчезли в пределах2с, максимум наблюдаемого ожидания33мс |

Снимки ps после EPERM в последнем сценарии уже не находили участников группы: состояние успевало измениться между системными вызовами. Поэтому по этим снимкам нельзя приписать конкретный zombie каждому отказу. Детерминированный эксперимент с zombie выше подтверждает механизм отдельно.

Настоящий worker запускает guardian без новой session: он находится в той же группе процессов. Поэтому воспроизведённый механизм совместим со схемой проекта и traceback предыдущей пробы. **Связь с конкретным прошлым отказом — обоснованная гипотеза**: снимка состава группы в момент того EPERM нет. Нехватка памяти и изменение UID не доказаны.

## Исправление

При `PermissionError` проверка теперь сообщает registry: отсутствие группы не подтверждено. Registry продолжает ограниченное ожидание по прежним TERM/KILL/deadline-пределам. Только `ProcessLookupError`/ESRCH подтверждает отсутствие группы.

Если EPERM сохраняется до окончания ожидания, stop возвращает false, registry сохраняет дескрипторы, а действующая логика controller оставляет RECOVERY_REQUIRED. Отказ не объявляется успешной очисткой. Новый таймаут, повышение лимитов и отправка сигналов уже забранному лидеру не добавлены.

Изменение находится только во внешнем process adapter `_group_exists`. Политики обработки, DTO, БД, правила публикации и владение процессами не менялись.

## Подтверждение исправления

Два поведенческих теста сначала упали на PermissionError, затем прошли:

- Временный EPERM: registry продолжает ждать и завершает stop только после ESRCH.
- Постоянный EPERM: stop возвращает false, registry не очищается; группе уже завершённого лидера отправляются только проверки с сигналом0.

Native проверка текущего registry:20синтетических worker+guardian завершились успешно; все группы исчезли. В этой серии проверки registry видели ESRCH, а не EPERM, поэтому она подтверждает нормальный teardown; обработку отказа отдельно проверяют тесты с контролируемым EPERM.

153релевантных теста прошли за30,75с; один существующий Starlette/httpx warning. Ruff и `git diff --check` прошли. Все созданные группы проверены на исчезновение, приватные временные lease-каталоги native проверки удалены. Свидетельства диагностики сохранены в приватном пакете прошлой пробы; её исходные журналы не переписаны.
