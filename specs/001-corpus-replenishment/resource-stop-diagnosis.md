# Диагностика RESOURCE_STOP на повторной серии

Дата: 2026-10-15. Статус: **PARTIALLY_DIAGNOSED / DIAGNOSTICS_IMPLEMENTED**.

Проверены приватные resource observations, controller/worker diagnostics, последняя telemetry и код защиты из [прерванной серии](sequential-batches-repeat-report.md). Новый ML-прогон и БД не запускались.

## Что установлено

Первый STOP возник в ветке ошибки обязательного наблюдения `MacResourceObserver`, а не в итоговой ветке превышения общего RSS/MPS или критического давления памяти. Это более точный вывод, чем первоначальное UNKNOWN по итоговой причине STOP; конкретная неуспешная проверка по-прежнему UNKNOWN.

Основание: непосредственно перед первым STOP есть успешное наблюдение. В первом STOP сохранены pressure1/RSS699809792/MPS2711306240 — тот же предыдущий `last_sample`. В исходном коде ветка лимитов сначала обновляет `last_sample`, затем проверяет pressure4, RSS и MPS выше6GiB. С сохранёнными значениями ни один из этих предикатов не выполняется. Ветка перехваченного исключения, напротив, выдаёт STOP без замены `last_sample`. STOP фиксируется до последующего SIGTERM worker.

Внутри обязательного наблюдения есть также отдельная проверка worker RSS ceiling: она выдаёт исключение до обновления last_sample. Поэтому превышение именно component ceiling не исключено, даже если итоговая ветка общих лимитов не была причиной STOP. Ранее произнесённое «не из-за достижения 6 GiB» было слишком категоричным.

Предшествующие WARNING/pressure2 подтверждены, но не устанавливают, какое измерение позже завершилось ошибкой. Телеметрия продолжала записываться близко к первому STOP: её последний сохранённый timestamp немного позже начала этого наблюдения. Последний файл не сохраняет все прежние версии и не доказывает, что именно прочитал observer. Поэтому ни устаревание телеметрии, ни command timeout, ни ошибка process identity пока не установлены как причина этого прогона.

## Почему точной причины нет в старом журнале

Observer объединял исключения команды ОС, разбора process table, проверки controller/worker identity, worker RSS, чтения/идентичности/свежести telemetry и pressure в один STOP. Тип исключения и этап проверки не записывались. Возврат предыдущего успешного sample выглядел как текущие значения STOP. Старые приватные файлы не изменялись; дополнительные сведения задним числом не созданы.

## Что добавлено

В существующие private resource observations добавлено поле `diagnostic`:

| Поле | Значение |
|---|---|
| `reason` | OK/WARNING, OBSERVATION_FAILED либо PRESSURE_CRITICAL/RSS_LIMIT/MPS_LIMIT |
| `check` | Фиксированный код этапа: PROCESS_TABLE, CONTROLLER_IDENTITY, WORKER_IDENTITY, WORKER_RSS, TELEMETRY_READ, TELEMETRY_IDENTITY, TELEMETRY_FRESHNESS, PRESSURE_READ, OBSERVATION_FRESHNESS, RESOURCE_LIMITS |
| `error_type` | Тип исключения из ограниченного списка, OTHER для остальных; null при штатном измерении |
| `sample_current` | true, если измерение завершено; false, если `sample` является предыдущим успешным замером либо отсутствует |

При повторном обращении после STOP сохраняется первая диагностика остановки. Значения путей, argv, stderr, nonce и произвольные сообщения исключений не записываются. Нового потока, сервиса, OS/DB/GPU polling и нового файла нет; запись остаётся в существующем ограниченном журнале. Размер строки увеличился; фактический overhead ML не измерен. Ограничение размера журнала остаётся действующим.

WORKER_RSS с OBSERVATION_FAILED может означать как выход за component ceiling, так и недостоверный ceiling: это код проверки, а не утверждение о нехватке памяти. Несколько одновременно нарушенных лимитов представлены первой выбранной причиной; журнал не является полным перечнем всех возможных нарушений.

`RecordingResourceObserver` по-прежнему останавливает работу при собственной ошибке записи/fsync/лимите журнала. Такие ошибки могут не попасть в тот же неисправный журнал. Новое поле раскрывает причины sensor STOP, но не обещает сохранение причины при любом сбое самого хранилища диагностики.

## Проверка и границы

TDD: пять новых сценариев сначала упали из-за отсутствия диагностики, затем прошли: OS command timeout, stale telemetry, critical pressure, MPS ceiling и worker RSS check. Каждый проверяет запись причины в JSONL, актуальность sample, сохранение первой причины и отсутствие секретного текста. Проверка размера журнала обновлена под увеличившуюся строку: одна запись помещается, следующая закрывает admission без переписывания исходной.

119релевантных тестов runtime binding, host, monitor, worker binding, controller, operation log, load diagnostics и boundaries прошли. Ruff и форматирование проверены. Первый тестовый вызов без PYTHONPATH не собрал пакет, другой со старым несуществующим именем test-файла не выполнил тесты; эти вызовы не считаются RED. RED подтверждён отдельным корректным запуском пяти новых сценариев.

Ресурсные пределы, freshness, защёлкивание STOP и отсутствие автоматического рестарта сохранены. Изменились только диагностические сведения адаптера; core DTO не менялся. Независимое review не проводилось. Нормативные требования, рабочий корпус/Web и лимиты не менялись; commit/push/merge не выполнялись.

Изменение runtime-кода делает ранее замороженные execution packages неактуальными. Для получения точной причины в новом реальном исполнении нужны свежий пакет, проверка предусловий и отдельный допуск по [quickstart](quickstart.md). Эта задача не выполняла повторный START/RESUME и не доказала устранение исходного measurement failure.

Результат следующей разрешённой серии 2026-10-15: [обе партии выполнены успешно](resource-stop-diagnostic-report.md),395наблюдений с новой diagnostic всеOK. Ошибка не воспроизвелась; конкретная причина прошлого STOP остаётся UNKNOWN. Успешный повтор не является подтверждением устранения исходного failure.
