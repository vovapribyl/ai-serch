## Результат

Локальный CLI разбирает `start`, `resume`, `retry-photo`, `retry-publication`
и `status`. Неизвестные и повторные параметры отклоняются. Частные JSON-файлы
проверяются по правам, владельцу, размеру и схеме; symlink не принимается.
Help не подключает БД и модели. Входной inventory и профиль проверяются
до смены режима и мутаций БД.

Клиент отправляет команду через owner-only Unix socket в каталоге 0700,
socket 0600. Сервер использует уже удерживаемый supervisor mode lease;
CLI не захватывает его повторно и не запускает независимый ML-процесс.
CHECK допускается только к status. Повторный start получает BUSY и не меняет
репозиторий активного запуска. Пакеты, ответы и ожидания IPC ограничены;
после отправки без подтверждённого ответа возвращается UNKNOWN, без повторения.

Публичный JSON содержит только разрешённые поля summary и коды причин.
Raw paths, дополнительные поля и текст внутренних исключений в вывод не проходят.
Реализованы exit codes 0/2/3/4/5/6. Код 0 для status означает успешное чтение;
ошибки отдельных фото остаются видны в outcomes и сами по себе не запрещают код 0.

Композиция start связывает supervisor, controller, файлы и PostgreSQL-адаптер:

1. Проверить пакет и отдельный допуск build; закрыть выдачу query permits.
2. Дождаться завершения поиска, подтвердить teardown и ресурсы, выдать новый owner.
3. Зафиксировать inventory и партию; пройти локализацию и три encoder-стадии.
4. После обработки партии подготовить и публиковать каждый готовый товар.
5. Сохранить исход запуска; вернуть SEARCH только после teardown, свежих ресурсов
   и отдельного разрешения поиска. При неподтверждённом завершении — RECOVERY_REQUIRED.

Товар без успешных фото получает NOT_PUBLISHABLE. Ошибка одного фото не теряет
пригодный результат другого. Status читает из БД выбранные фото, outcomes,
оставшиеся стадии, редакции и состояния публикаций; режим поиска берёт у supervisor.

Drain, controller, SQL и teardown используют общее конечное окно. Controller
не начинает даже итоговое чтение БД после cutoff. Только запись исхода завершения
может использовать оставшийся cleanup reserve; checkpoints и публикация не могут.
Истечение срока сохраняет EXPIRED и не открывает поиск автоматически.

В текущем target Web-приложении нет готовой ветки busy для поиска. Минимальный
hook `search_available` показывает HTTP 503 с понятным текстом при закрытом
или неизвестном admission. При отсутствии hook прежний экран сохраняется.
Новых Web-операций пополнения нет, source Web-файл целиком не переносился.

## Ограничения и следующий этап

Временные контейнеры удалены. Модели и векторы в проверках синтетические;
реальные фото, weights, HTTP I, MPS и рабочая БД не запускались.
Установка зависимостей, commit, push и merge не выполнялись.

Грамматика resume/retry готова; соответствующие application-операции пока
возвращают NOT_IMPLEMENTED, код 5. Их реальная логика и интеграция остаются
в пунктах 036–046. Startup recovery и warning/wait также ещё предстоят.
Это не утверждение завершения всей функции.

Сервер предоставляет bounded `serve_once`; постоянно работающий host и настоящие
ML-worker factories этим прогоном не поднимались. Callback-допуски build/search,
наблюдения ресурсов и worker были fake. Реальное подключение требует нового
runtime package и допуска 049–050. Пользовательский backend не переключён;
полноценная Web-страница поиска из source checkout не объединялась с target.

Независимое review не проводилось: STANDARD, самопроверка и TDD; итоговое review
остаётся в пункте 051. Применены Superpowers и CleanArchitecturemini: policy
controller остаётся чистым, SQL/IPC/OS/Web и композиция — снаружи. Причинный эффект
правил и экономия ресурсов не измерялись.
