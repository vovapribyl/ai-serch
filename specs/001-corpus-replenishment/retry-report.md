# Явный повтор фото и публикации

2026-10-14. Пункты 043–046 [плана задач](tasks.md), STANDARD.
Ветка `codex/upload-optimiz`; проверки в пределах синтетического [B1](test-execution-package.md).

## Результат

`retry-photo` принимает текущую редакцию, одно выбранное ERROR-фото и ожидаемую
версию указателя товара. Проверка входов, профиля и версии выполняется до смены
режима; под блокировками она повторяется перед записью. Новая редакция содержит
полный прежний список фото. Только выбранное ERROR становится PENDING.
Остальные ERROR, NO_NAILS, OK и ещё не выбранные PENDING сохраняют свои исходы;
другие ошибки автоматически не запускаются.

Пригодные неизменённые результаты ссылаются на исходные immutable checkpoints.
Nullable `revision_photos.reused_from` в ещё не развёрнутой миграции0010 хранит
такую связь. FK и trigger проверяют товар, профиль, идентичность фото и исход;
ссылка не переписывает original attempt или manifest. При следующем ручном
повторе ссылка ведёт к первоначальному результату, без цепочки промежуточных
редакций. Подготовка новой READY проверяет файлы и переносит области/векторы
в новую редакцию. Старые опубликованные редакции и снимки сохраняются.

Создание новой редакции и смена current head происходят в одной транзакции.
Конфликт версии откатывает clone; старый активный каталог остаётся доступным.
Успешное либо чужое фото нельзя передать вместо выбранной ошибки.

`retry-publication` не создаёт редакцию и не вызывает worker factory. Он использует
READY-результаты текущей редакции. Для FAILED создаётся новая попытка в новом
допустимом запуске; старая FAILED остаётся в истории. Если уже есть receipt,
повтор не создаёт ещё один снимок или publication.

UNKNOWN сначала сверяется. Новый owner выдаётся только после подтверждённого
завершения прежних workers. Под owner/run/head/revision locks предыдущие writers
уже fenced: наличие receipt означает SUCCEEDED; отсутствие receipt позволяет
зафиксировать RECONCILED_ROLLBACK и начать явно разрешённый повтор. Если сверку
или завершение подтвердить нельзя, новая публикация не начинается.

Команды используют прежний частный CLI/IPC и общий deadline/admission.
Грамматика не расширялась; ни `--force`, ни автоматического retry нет.
Пакет retry должен связывать полный список фото выбранного товара с неизменным
профилем; реальные пакеты и runtime ещё требуют отдельного допуска.

## Решения реализации

- Ожидаемая версия относится к current head: именно он канонически определяет
  текущую редакцию в принятой модели. Неверная версия даёт отказ до выдачи owner.
  Ошибка такой интерпретации потребовала бы согласовать иной контракт аргумента.
- Для reuse выбрана ссылка на исходное фото в миграции0010, которая применялась
  только к новым синтетическим БД. Это сохраняет identity файлов; развёрнутой
  рабочей БД с этой миграцией нет. Для уже развёрнутой схемы понадобилась бы
  отдельная upgrade migration.
- Одна команда повторяет одно фото, как в принятой грамматике. Массовый retry
  не добавлен; для него потребовался бы отдельный контракт выбора и лимитов.
