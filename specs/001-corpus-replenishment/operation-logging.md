# Журнал обработки поискового корпуса

Статус: реализовано в текущем коде; проверено на синтетических процессах и полном реальном цикле пяти фото. [Реальная проба](operation-log-probe-report.md) остановилась после локализации и OpenCLIP из-за PermissionError проверки process group. Журнал сохранился; обнаруженный дефект признака ожидаемой остановки исправлен по TDD. После исправления нового ML-прогона не было.

Основание: владелец согласовал добавление журнала после обсуждения стоимости логирования 2026-10-14. Изменение относится к наблюдению работы controller и не меняет правила обработки, публикации, восстановления или ресурсные ограничения.

## Что можно увидеть

Controller записывает начало, результат и ошибку обработки партии, открытия стадии, обработки фото на стадии, записи checkpoint и публикации. Для worker сохраняются PID, стадия, модель, код выхода, номер сигнала и признак того, что остановку запросил controller. При ресурсной остановке сохраняется известный код причины. Время события и порядковый номер помогают восстановить последовательность; разница времён границ даёт длительность вызова, включая ожидания.

Успешное возвращение метода публикации не обязательно означает публикацию: журнал сохраняет `result_state`, в том числе `UNKNOWN`. Источником состояния остаётся БД. Повторная обработка и восстановление по одному журналу не выполняются.

Ссылки на run, revision, photo и attempt заменяются псевдонимами с солью отдельного запуска controller. Они связывают события внутри этого журнала, но не служат общим ключом между разными запусками. Исходные идентификаторы товаров, фото, изображения, векторы, SQL, параметры соединения и тексты исключений не записываются. Ошибка содержит тип, известный безопасный код остановки или `UNKNOWN`; для `OSError` — числовой `errno`. Подробные безопасные кадры ошибки команды остаются в существующем отдельном `command-failure.json`.

## Где хранится журнал

Параметр `operation_log_root` в замороженном runtime binding задаёт существующий абсолютный приватный каталог владельца с правами `700`. Он входит в hash runtime binding. Если параметр отсутствует, используется `shared_runtime_root`. Файлы получают права `600`, а каждый запуск controller создаёт отдельный каталог `operations-*`:

| Файл | Назначение |
|---|---|
| `events.jsonl` | Последние события, одна JSON-запись на строку |
| `events.1.jsonl`, `events.2.jsonl` | Два предыдущих фрагмента после ротации |
| `status.json` | Полнота записи и число ротаций при закрытии журнала |

Каждый файл событий ограничен 1 МиБ; после ротации сохраняются три последних файла. Старые события этого запуска могут быть вытеснены. `sequence` позволяет обнаружить начало сохранённого фрагмента. Лимит относится к одному запуску, а не ко всему каталогу. Автоматическое удаление журналов старых запусков и срок хранения не добавлены.

Для постоянного хранения каталог должен находиться на постоянном диске вне репозитория и временных каталогов. Сам журнал не превращает `/tmp` в постоянное хранилище. Рабочий каталог для эксплуатации в этой задаче не создан и не перенастроен; тесты используют временные приватные каталоги.

## Запись и сбои

Обычные события записываются сразу через буфер ОС без `fsync` на каждую строку. Ошибки, выход worker, завершение controller и успешный возврат методов checkpoint/публикации синхронизируются на диск. Ротация также синхронизирует файл и каталог. Дополнительного опроса памяти, GPU или Docker этот журнал не делает. Существующие resource observations и включаемая подробная диагностика сохраняют прежний режим работы.

Невозможность открыть журнал при запуске не позволяет начать обработку. Если запись ломается во время работы, журнал помечается неполным; исходный результат или исключение обработки сохраняется. При недоступном диске может не сохраниться и `status.json`. Отсутствие файла состояния означает неизвестную полноту, а не успешное завершение.

Controller фиксирует код выхода worker до удаления дескриптора процесса; финальная строка самого worker для этого не нужна. Если controller остановил worker после `RESOURCE_STOP`, код этой причины сохраняется отдельно от сигнала. Внешний SIGKILL сам по себе не доказывает OOM. При гибели самого controller запись его завершения может отсутствовать; автоматический диагноз причины, проверка журналов при следующем старте и fault injection реальных моделей не добавлены.

## Проверка и ограничения

TDD проверяет сохранение аргументов, результата и исходной ошибки, отсутствие приватных значений, права файлов, ротацию, сбой записи и безопасные коды ошибок. Синтетические собственные subprocess проверяют штатный SIGTERM и неожиданный SIGKILL: controller сохраняет ровно одну запись выхода без worker footer. Проверка реального wiring host использует подменённую БД и датчики, с подробной диагностикой и без неё.

Итоговая проверка: 150 релевантных тестов прошли за31,50с; один существующий warning Starlette/httpx. Ruff, форматирование и `git diff --check` прошли.

Нагрузка журнала в реальной ML-партии не измерена. Итоговые worker-файлы подробной диагностики из прошлых прогонов остаются `UNKNOWN`; это изменение даёт отдельное свидетельство выхода процесса и не исправляет прошлые артефакты задним числом.

После изменения кода прежние замороженные пакеты нельзя повторно использовать. Для реальной проверки нужно подготовить свежий пакет и получить отдельное разрешение на его запуск по [quickstart](quickstart.md). Запуск нескольких сотен фото этим изменением не разрешён.
