# Повторная проверка двух последовательных партий

Дата: 2026-10-15. Статус: **EXECUTED / STOPPED_RESOURCE_STOP**.

Подготовлен свежий контур после [остановки первого запуска](sequential-batches-report.md). Владелец разрешил подготовку, затем запуск обоих пакетов. Попытка A остановлена на локализации по RESOURCE_STOP; B не запускалась. [Отчёт исполнения](sequential-batches-repeat-report.md). Проверки подготовки ниже сохранены как история перед запуском.

## Что запускаем

Две партии по пять фото в одной новой временной БД, последовательно. Те же десять разных входов, модели, semantic profile, 81 файл продуктового кода и лимиты, что в [исходном предложении](sequential-batches-proposal.md). Там описаны входы, проверка накопления 0 → 5 → 10 и сохранности первых товаров, SQL-checkpoint, значений векторов и фактических файлов.

Новые SHA:

- A: `fc15b466d06e3bc79b827a0ade09ef35db2c1d390936465fc1020254a940282f`.
- B: `6ca131013478f695f9152544694299755ab7591326d57cf67075989b339744fe`.

Новые runtime paths, target marker и proposal nonces входят в новые fingerprints. Старые гранты и контур не используются. Наборы изображений и их байты совпадают с не начавшими обработку A/B предыдущей попытки; новых фото в scope не добавлено.

Runner закреплён SHA-256 `16311b4d0f68c247422dad9554d70b70c683947a4534eebd0b9c0996819719d5`. Путь readiness берётся из client configuration, SQL tuple сравнивается с tuple, ранний результат фазы и ограниченный код ошибки сохраняются. Это исправления тестового инструмента; продуктовый код не менялся.

## Что проверено до запуска

- Для обеих фаз прошли hashes/code inventory/input bytes/DTO/права; десять входов различаются между партиями, общий target/checkpoint/runtime согласован.
- Две metadata-only сборки локализатора прошли без SDK и сервера. Шесть проверок реальных interpreter entrypoints отвергли proposed control с code5; inventories совпали. Это проверки отказа без допуска, не успешная загрузка моделей.
- Выражение ожидания из исправленного runner проверено с реальным временным Unix socket в общем каталоге, отличном от каталога A. Существующий socket пропускает ожидание, отсутствующий даёт ограниченный timeout. Тестовый socket удалён. Bind потребовал снятия sandbox-ограничения; DB/host/ML при этом не запускались.
- Проверки tuple-счётчиков для 5/10 товаров принимают полный результат и отклоняют неполный. Обработчик ранней ошибки сохраняет фазу и код. Проверен синтаксис runner.

Полный runner после исправления ещё не выполнялся. Последние 163 теста продуктового кода — историческая проверка, повторно не запускались, поскольку код не изменён. Полный rehash encoder weights не повторялся; native проверяет их перед загрузкой. Live pressure, quiescence и отсутствие посторонних probe-контейнеров проверяются непосредственно перед разрешённым запуском; текущая подготовка не заменяет эти условия. Review не проводилось.

## Граница допуска

Получено разрешение ровно этих двух пакетов: одна собственная временная PostgreSQL, два START, разные свежие одноразовые гранты, отдельный readonly monitor каждой фазы. B только после полной успешной проверки A и закрытия её host/workers/viewer. При неполном результате серия останавливается, автоматического повтора и замены фото нет.

Лимиты прежние: 1200с и 24 ML admissions на партию, общий runner2520с с подготовкой и очисткой; RSS/MPS6GiB, encoder RSS5GiB; resource wait300с/stability30с. Остальные пределы и параметры БД — по исходному предложению. После успеха или ошибки очищается только собственный тестовый контур; оставшийся socket дополнительно проверяется после остановки процессов. Приватные свидетельства сохраняются.

RESUME, третья партия, crash injection, увеличение лимитов, рабочая БД/Web, установка зависимостей, commit/push/merge не входят в этот допуск. Отдельное разрешение на реальное исполнение предусмотрено [quickstart](quickstart.md#первый-этап049--2026-10-14-историческая-запись): «после изменения code/runtime пакет замораживается заново. Затем отдельное owner разрешение050 на ML/testinputs/изолированнуюDB/publication».
