# Где возникает нагрузка при пополнении корпуса

Дата: 2026-10-14. STANDARD: анализ сохранённых свидетельств и кода,
без новых модельных запусков и изменения алгоритмов.

## Установленный результат

В двух исследованных пробах самая большая измеренная память MPS относится
к **процессу локализатора I**. В партии пяти фото остальные три модели ещё
не запускались: остановка произошла внутри стадии localization перед записью
пятой SQL-контрольной точки. Одновременно трёх encoders в этой пробе не было.

Непосредственная причина ожидания — системный сигнал **pressure=2**.
По MacResourceObserver он переводится в WARNING независимо от величины MPS.
Потолок MPS 6 GiB не превышен; 5,82 GiB сами по себе не являются порогом WARNING.
После 300 с без восстановления допустимых условий команда вернула WAIT_TIMEOUT.
Давление измеряется для всей машины, поэтому оно не доказывает исключительную
виновность I или отсутствие вклада фоновых приложений.

## Сравнение стадий по сохранённым замерам

Источник: resource-observations.jsonl двух разрешённых пакетов, сгруппированный
по context.stage_key/model_key. Исходные файлы и пути остаются приватными.
Пакет одного фото — 7d89d5da, пяти фото — cfe49786.

| Одно фото: I | 3,77 | 1,14 | 147 / 6 / 0 |
| Одно фото: OpenCLIP | 0,36 | 1,03 | 17 / 0 / 0 |
| Одно фото: DINOv2 | 0,35 | 0,52 | 12 / 0 / 0 |
| Одно фото: SigLIP2 | 0,39 | 0,53 | 17 / 0 / 0 |
| Пять фото: I | 5,82 | 1,39 | 293 / 1151 / 0 |
| Пять фото: три encoders | Не запускались | Не запускались | Нет измерений |

Дополнительно по четыре OK-наблюдения без ML worker в каждой пробе.
На стадии I каждой пробы наблюдался один принадлежащий запуску ML worker.
RSS в таблице — controller плюс группа ML worker, включая его дочерний guardian,
а не отдельный RSS самой нейросети. Начальный controller без ML имел пик около
44,5 MiB. Память PostgreSQL отдельно этим наблюдателем не измерялась.
RSS и MPS не суммируются: CPU/GPU используют общую память.

Метрика MPS снимается через torch.mps.driver_allocated_memory(): в неё входят
не только живые тензоры, но и кеш allocator и выделения MPS/MPSGraph.
Доли этих составляющих сейчас неизвестны. Частота выборки не гарантирует
регистрацию каждого кратковременного пика.

В партии пять localization manifest содержат 10, 3, 10, 5 и 4 региона,
всего 32. Они появились примерно через 17,0; 21,4; 58,3; 62,3; 98,1 с
после начала подготовки запуска (по mtime файлов). Полный запуск занял 404,117 с.
Этот интервал включает ожидания, загрузку и очистку; его нельзя объявить временем
чистого inference. Последний результат остался только в файлах, SQL checkpoints — четыре.
Прямое сопоставление wall-clock mtime и monotonic timestamp ресурсных записей
не использовано: доступная оценка смещения часов не дала надёжного соответствия.

## Почему старый прогон на 674 фото не противоречит этому результату

[Gate 2](../../docs/gate-2.md) подтверждает импорт 674 записей и файлов.
Индексация тремя моделями подтверждена в историческом Gate 3: по 674 вектора
OpenCLIP, DINOv2 и SigLIP2, всего 2022; модели запускались последовательно.
Канонический исторический dossier находится в owning worktree e727,
docs/gate-3.md, §12: строка «Embeddings count по рабочим моделям».
Содержимое модели и исторические веса здесь не перезапускались.

| Условие | Исторический Gate 3 | Текущее пополнение |
|---|---|---|
| Вход в encoder | Целое фото | Области ногтей, найденные локализатором |
| Подготовка областей | Нет Grounding DINO / SAM2 в index_active_corpus | I: Grounding DINO + SAM2.1 Hiera Small |
| Объём векторов | Один на фото на модель | До десяти на фото на модель |
| Работа моделей | Последовательно, подтверждено dossier | Отдельные workers по стадиям; encoders партии ещё не начались |
| Ресурсные свидетельства | Завершение 674/674 каждой модели подтверждено; сопоставимые пики отсутствуют | Есть RSS/MPS/pressure по стадиям и ограниченное ожидание |

Успешные 674 изображения доказывают работоспособность прежней индексации.
Они не доказывают, что новый локализатор выдержит ту же нагрузку или что прежний
прогон применял идентичную ресурсную защиту. Продолжительность и сопоставимые
CPU/GPU-пики исторического прогона в изученных источниках не установлены.

## Что показывает код локализатора

1. LazyLangSAMClient удерживает объект LangSAM между запросами.
2. LangSAM содержит две модели: детектор Grounding DINO и сегментатор SAM2.
   Они находятся в одном worker. Grounding DINO использует resize: shortest edge
   800, longest edge 1333; малый исходный файл не означает малые промежуточные тензоры.
3. В текущем профиле включён TwoPassRoiLocalizer: при подходящем ROI возможен
   второй вызов локализации. Фактическое количество проходов на каждом фото не записано.
4. SAM2 predictor сохраняет features последнего изображения до reset_predictor
   следующего set_image_batch. После ответа явного reset в LangSAM.predict_batch нет.
5. Во время _admit_resources процесс I остаётся живым. poll_resources только
   ждёт следующего наблюдения; само ожидание не выгружает модель и не очищает её кеш.

Это объясняет, где искать удерживаемую память, но не доказывает утечку.
Рост driver memory с 3,77 до 5,82 GiB может включать кеш, временные выделения,
различия фото/числа областей и работу двух проходов. Какой именно компонент
доминирует внутри I — **UNKNOWN**. Наличие no_grad в GDINO и SAM2 также проверено;
гипотеза накопления графов обучения не подтверждена.

## Какие измерения нужны, чтобы отделить причины

Следующая диагностическая проба должна сохранять компактные метрики в точках:
до загрузки; после загрузки I; до/после Grounding DINO; до/после SAM2;
после нормализации ответа; перед checkpoint; во время ожидания; после закрытия worker.
Второй ROI-проход отмечается отдельно; фото обозначаются приватными порядковыми номерами.

Нужны:

- current_allocated_memory вместе с driver_allocated_memory: живые тензоры
  отдельно от общего driver allocation; их разница не является точным размером кеша;
- RSS и накопленное CPU-время каждого процесса: controller, I worker, guardian,
  затем каждого encoder; отдельно память временной PostgreSQL;
- системные pressure, swap и доступная память с отметками времени;
- длительности GDINO/SAM2, число проходов и найденных областей;
- единая привязка wall-clock и monotonic при старте, чтобы уверенно связать фото и замеры.

Сначала измеряем существующий алгоритм. Проверка очистки кеша или SAM features —
отдельная гипотеза с одним изменением и проверкой неизменности результатов.
Повышать потолки или отключать модели по текущим данным оснований нет.
CPU-нагрузка, загрузка GPU в процентах, разбивка памяти между GDINO/SAM2 и вклад
чужих процессов пока не измерены. Новый ML-прогон потребует подготовленного пакета
и отдельного допуска; здесь он не выполнен.

## Дополнение: реальные замеры внутри I

[Диагностический прогон de3c9c6e](load-diagnostics-report.md) завершился OK на
пяти фото при pressure=1. Главный прирост driver между границами вызовов
зафиксирован у GDINO, live tensors после вызовов почти стабильны около1,16GiB,
driver до5,83GiB. Установлено место прироста, но точное разделение allocator cache/
MPSGraph и причина отличия системного давления UNKNOWN. Сохранились все границы
модельных вызовов; final worker status отсутствует, teardown telemetry неполная.

## Дополнение: освобождаемая часть MPS-кеша

[Проверка99cea844](mps-cache-probe-report.md) подтвердила эффект на тех же пяти фото:
empty_cache после каждого фото снижал driver примерно на1,0–1,2GiB при неизменных
live до/после операции. Наблюдённый максимум3,77GiB вместо5,83GiB,послеphoto5 —
2,56GiB вместо5,80GiB.32crops/32mask bytes совпали,полный tempDB cycleOK.
Это подтверждение освобождаемой части памяти в этой пробе,не полный разбор
MPSGraph,не устранение причин системного pressure2 и не оценка устойчивости674фото.
