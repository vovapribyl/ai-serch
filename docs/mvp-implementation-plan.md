## 1. Результат и граница плана

План ведёт от пустого кодового контура до локального MVP, который прошёл применимые проверки [`ART-09`](analysis/09-acceptance-criteria-and-traceability.md). Разработка идёт короткими TDD-инкрементами и останавливается на четырёх понятных владельцу gates.

План не запускает разработку. Установка Docker, загрузка весов моделей и создание кода начнутся только после отдельной команды владельца.

В MVP входят:

- служебная загрузка полного XLSX-снимка;
- локальное хранение одного основного изображения записи;
- эмбеддинги трёх локальных моделей;
- точный поиск кандидатов через PostgreSQL с `pgvector`;
- локальный интерфейс загрузки фотографии и просмотра не более 10 кандидатов;
- показ доступных статусов и истории;
- результат `NEW / SAME_PRODUCT / UNCERTAIN`;
- отношение `VARIANT / UNRELATED / N/A` только в утверждённой предметной границе;
- помощник накопления и кнопочной разметки примеров;
- воспроизводимая проверка качества и времени ответа.

В MVP не входят:

- Google Sheets API и двусторонняя синхронизация;
- авторизация, роли и многопользовательская работа;
- создание или изменение карточек, статусов и корпуса из пользовательского интерфейса;
- `ANALOG`, текстовый поиск и OCR;
- MinIO, очередь, отдельные worker-процессы, HNSW и Qdrant;
- обучение модели с нуля;
- мобильный интерфейс, PWA и работа через камеру телефона.

## 2. Техническое направление

MVP строится как модульный монолит. Это позволяет развивать предметные и технические модули раздельно, но не добавляет сетевые границы между ними до подтверждённой необходимости.

Основной стек:

- Python 3.12 и FastAPI;
- Jinja2/HTMX для локального интерфейса;
- PostgreSQL с расширением `pgvector` через Docker Compose;
- Alembic для миграций;
- `pytest` для unit-, интеграционных и контрактных тестов;
- локальная файловая система за интерфейсом `ImageStorage`;
- локальные OpenCLIP, DINOv2 и SigLIP2 за интерфейсом `EmbeddingProvider`.

PostgreSQL выполняет точный поиск по косинусной близости. При ожидаемом масштабе MVP приближённый индекс не добавляется без измеренной проблемы производительности.

### Минимальные технические сущности

Начальная схема содержит только данные, необходимые утверждённому MVP:

- `CorpusVersion` — загруженная версия полного снимка и признак активной версии;
- `ProductRecord` — запись товара с постоянным `product_id`, `source_row`, категорией, доступным статусом и историей;
- `ProductImage` — основное изображение, его путь, формат и SHA-256;
- `Embedding` — вектор, модель, версия весов и параметры препроцессинга;
- `ImportOperation` — одна попытка служебной загрузки;
- `ImportIssue` — критическая ошибка или причина исключения строки;
- `EvaluationExample` — локальный пример разметки и его состояние;
- `EvaluationRun` — воспроизводимый запуск модели на зафиксированной выборке.

`SearchRequest`, `UserFeedback`, `ProductRelation` и полный бизнес-жизненный цикл не создаются заранее. Они вернутся в проектирование только после отдельного post-MVP решения.

`EvaluationExample` не является пользовательской обратной связью продукта. Это техническая запись контрольного примера, которая существует только в локальном evaluation-контуре.

## 3. Как применяется TDD

Test-Driven Development (TDD) управляет программным поведением. Каждый небольшой инкремент проходит один цикл:

1. Исполнитель записывает ожидаемое поведение в тесте.
2. Тест воспроизводимо завершается с `FAIL` по нужной причине.
3. Исполнитель добавляет минимальную реализацию.
4. Тест и применимый набор регрессии завершаются с `PASS`.
5. Исполнитель улучшает структуру кода без изменения поведения.

Положительный тест, написанный после готовой реализации, не считается доказательством полного TDD-цикла. Для значимого поведения отчёт инкремента сохраняет короткое свидетельство `fail → pass`.

### Уровни проверки

| Уровень | Что проверяет | Примеры |
|---|---|---|
| Unit | Чистые правила без инфраструктуры | формат `product_id`, причины отклонения, бизнес-классификация |
| Интеграционный | Совместную работу с PostgreSQL и файлами | миграции, атомарная активация корпуса, точный векторный поиск |
| Контрактный | Границы API и отчётов | HTTP-ответы, JSON-отчёт импорта, ошибки входного файла |
| UI | Наблюдаемое действие пользователя | загрузка фотографии, кнопочная разметка, повтор после `UNCERTAIN` |
| Evaluation | Качество модели на зафиксированных данных | Recall@10, ложный уверенный `SAME_PRODUCT`, время ответа |

ML-evaluation не подменяется unit-тестами. Программный тест доказывает правильность расчёта метрики, но не доказывает качество модели на реальных товарах.

## 4. Gate 1 — воспроизводимый технический каркас

### Цель

Создать минимальное окружение, в котором следующий разработчик может запустить приложение и тесты на чистой машине.

### TDD-инкременты

1. Зафиксировать правила зависимостей модулей и проверить их структурным тестом.
2. Поднять PostgreSQL с `pgvector` через Docker Compose.
3. Добавить пустую схему Alembic и проверку миграции с нуля.
4. Реализовать health-check приложения и БД.
5. Создать пустой локальный экран загрузки без поисковой логики.
6. Подключить временную директорию через интерфейс `ImageStorage`.
7. Настроить приложение только на loopback-интерфейс локальной машины.
8. Разместить рабочий каталог данных вне Git-репозитория и запретить конфигурацией путь внутри репозитория.
9. Проверить, что MVP запускается из учётной записи владельца проекта или исполнителя MVP, а рабочий каталог недоступен другим локальным пользователям; завершать запуск с ошибкой при небезопасных правах каталога.
10. Проверить удаление временных файлов после успешной операции и после ошибки.
11. Добавить проверку Git и состава поставки на отсутствие корпуса, изображений, отчётов и весов.

### Свидетельства gate

- инструкция запуска на чистом окружении;
- автоматический отчёт тестов;
- применённая с нуля миграция;
- локально открытый экран;
- рабочие пути без раскрытия данных, результат проверки прав доступа и состава поставки;
- список технических гипотез, которые ещё не проверены.

Владелец проверяет только доступность экрана и понятность направления. Техническую корректность проверяют тесты и независимый reviewer.

## 5. Gate 2 — безопасная загрузка корпуса

### Цель

Загрузить подготовленный XLSX полным снимком и не повредить действующий корпус при критической ошибке.

### TDD-инкременты

1. Создать маленькие синтетические XLSX-fixtures с заранее известными строками и встроенными изображениями.
2. Извлечь `product_id`, `source_row`, категорию, основное фото и доступные поля истории.
3. Проверить цифровой `product_id` без ведущих нулей.
4. Исключить строку без категории или основного фото и записать причину.
5. Не использовать второе встроенное изображение вместо основного.
6. Заблокировать замену при повреждённом или нечитаемом XLSX.
7. Заблокировать замену при повторе `product_id`.
8. Загрузить допустимые строки в новую `CorpusVersion`.
9. Переключить активную версию только после успешной загрузки всех допустимых строк и файлов.
10. После успешной активации удалить DB-записи, изображения и эмбеддинги предыдущего корпуса. При ошибке сохранить предыдущий корпус без изменений.
11. Сформировать один локальный JSON-отчёт на операцию и применить срок хранения 90 дней.
12. Проверить удаление JSON-отчётов старше 90 дней и сохранение более новых.
13. Повторно проверить, что рабочие файлы и отчёты не попали в Git или поставку.
14. После прохождения синтетических fixtures выполнить защищённую локальную проверку `SRC-045` без публикации строк и изображений.

### Свидетельства gate

Владелец получает человекочитаемое представление JSON-отчёта:

```text
Снимок: corpus-2026-09-15
Принято: 642 строки
Отклонено: 32 строки
Без категории: 11
Без основного фото: 21
Повтор product_id: 0
Корпус заменён: да
```

Отдельные проверки показывают два результата: критическая ошибка оставляет предыдущий корпус активным; успешная активация удаляет прежние DB-данные и файлы. Свидетельство Gate 2 также подтверждает срок хранения отчётов и отсутствие ограниченных данных в Git и поставке.

## 6. Gate 3 — поиск и максимально простая разметка

### Цель

Получить работающий top-10 поиск и дать владельцу возможность накапливать реальные примеры без ручного ввода текста и идентификаторов.

### TDD-инкременты поиска

1. До загрузки реальных query-фотографий утвердить срок их хранения и удаления у владельца данных.
2. Реализовать утверждённую политику для query-фотографий, которые сохраняются как evaluation-примеры: удалять просроченные файлы и связанные записи, сохраняя непросроченные.
3. Проверить, что удаление evaluation-примера не оставляет осиротевший файл или запись, а сбой удаления фиксируется в техническом отчёте и не маскируется как успех.
4. Определить единый контракт `EmbeddingProvider`.
5. Подключить OpenCLIP, DINOv2 и SigLIP2 по одному контракту.
6. Зафиксировать имя модели, версию весов, контрольную сумму и параметры препроцессинга.
7. Запретить сетевые вызовы inference после локального получения и фиксации весов.
8. Проверить размерность и нормализацию эмбеддинга.
9. Сохранить отдельный эмбеддинг каждой модели.
10. Проверить точный порядок кандидатов на синтетических векторах.
11. Искать только в активной версии корпуса.
12. Ограничить продуктовую выдачу десятью кандидатами.
13. Проверить очистку временных query-файлов после успеха и ошибки.

Модели работают локально и последовательно. Изображения и эмбеддинги не отправляются во внешние сервисы.

### Кнопочная разметка

Помощник разметки относится к служебному evaluation-контуру, а не к пользовательскому сценарию `UC-001`. Поэтому он может показать дополнительные группы кандидатов для установления правильного ответа. Продуктовый поиск по-прежнему возвращает не более 10 кандидатов.

Пользователь выполняет один короткий поток:

1. Загружает фотографию.
2. Получает общий рейтинг кандидатов.
3. Выбирает карточку, только если хочет подтвердить или отклонить конкретного кандидата.
4. Нажимает одну кнопку: `Тот же товар`, `Вариант`, `Другой товар`, `Товара нет в корпусе`, `Не уверен` или `Пропустить`.
5. Для `Вариант` выбирает кнопкой: `Близкий оттенок`, `Количество в наборе`, `Комплектация` или `Другое отличие`.

Ручной ввод `product_id`, номера строки и комментария не требуется. Система сохраняет выбранный товар, класс, отличие, версии корпуса и моделей, позиции кандидатов и время разметки.

Кнопки формируют разметку однозначно:

- `Тот же товар` создаёт `TRUE SAME` и сохраняет выбранный `product_id`;
- `Вариант` с одним из трёх утверждённых отличий создаёт `TRUE VARIANT` и сохраняет выбранный `product_id`;
- `Другой товар` отклоняет только выбранного кандидата и возвращает пользователя к галерее; пример ещё не размечен;
- два последовательных подтверждения отсутствия товара в корпусе создают `TRUE NEW`;
- `Другое отличие`, `Не уверен` и `Пропустить` сохраняются для анализа, но не попадают в официальные метрики без отдельного решения.

### Общий рейтинг и оценки

Интерфейс показывает общий рейтинг, сводную оценку и оценки отдельных моделей. Оценка сопровождается пояснением: «Оценка сходства не является вероятностью».

Сырые оценки моделей не складываются: их шкалы различаются. Рабочая техническая гипотеза для общего порядка — Reciprocal Rank Fusion, то есть объединение позиций кандидата в списках моделей. Гипотеза проверяется детерминированными тестами и может быть заменена на Gate 3 без изменения требований.

Сначала интерфейс показывает 10 кандидатов. Кнопка `Показать ещё` открывает следующую группу. Если подходящего товара нет, пользователь может выбрать `Товара нет в корпусе`, `Не уверен` или продолжить просмотр.

`Товара нет в корпусе` требует дополнительного подтверждения кнопкой и не становится `TRUE NEW` автоматически. Неподтверждённый случай получает состояние «требует проверки» и не входит в метрики.

### Пилот

Пилотная цель — 60 реальных запросов: по 20 `TRUE SAME`, `TRUE NEW` и `TRUE VARIANT`. Меньший доступный объём не блокирует разработку.

Пилот:

- подтверждает работоспособность полного pipeline;
- выявляет повторяющиеся ошибки;
- позволяет исключить технически непригодную или явно слабую модель;
- не выбирает окончательную модель;
- не подтверждает приёмочные пороги.

Владелец проверяет разметку, понятность рейтинга и характер ошибок. Названия моделей и оценки видны по решению владельца; отчёт фиксирует возможное влияние этой информации на разметку.

## 7. Gate 4 — полный сценарий и техническая приёмка

### Цель

Закрыть применимые функциональные, data- и NFR-критерии и доказать качество поиска на данных, которые не использовались при настройке.

### TDD-инкременты сценария

1. Принимать JPEG и PNG размером не более 20 МБ.
2. Не запускать поиск без переданного файла, для неподдерживаемого файла или файла, превышающего лимит.
3. Показывать итог `NEW`, `SAME_PRODUCT` или `UNCERTAIN`.
4. Показывать `VARIANT / UNRELATED` только для категории с утверждёнными правилами; для `SAME_PRODUCT` показывать `N/A`.
5. Показывать доступные историю и статус кандидата.
6. Для `REJECTED_FOR_ASSORTMENT` без причины показывать «Причина отклонения не определена».
7. Показывать все доступные конфликтующие записи без автоматического выбора одной из них.
8. Позволять повторный поиск после `UNCERTAIN` без системного лимита повторов MVP.
9. При технической ошибке не возвращать бизнес-результат, не менять данные и записывать сведения об ошибке в технический отчёт.
10. Проверить, что поиск не изменяет корпус, Google Sheets, карточку, статус, категорию или роль.

### Сквозная перепроверка локального ограниченного контура

Базовые меры включаются до работы с реальным корпусом на Gate 1–2, а меры для query-фотографий и inference — до реальных примеров на Gate 3. На Gate 4 исполнитель повторно проверяет весь контур:

1. приложение слушает только loopback-интерфейс локальной машины;
2. каталог корпуса, query-изображения, отчёты, веса и производные файлы находятся вне Git-репозитория;
3. конфигурация не разрешает использовать каталог внутри репозитория как рабочее хранилище;
4. права рабочего каталога исключают доступ других локальных пользователей, а небезопасная конфигурация блокирует запуск;
5. временные файлы удаляются после успешной операции и после ошибки;
6. для сохранённых query-фотографий действует утверждённый владельцем срок: просроченные файлы и записи удаляются без осиротевших объектов;
7. JSON-отчёты старше 90 дней удаляются, а более новые сохраняются;
8. состав поставки и Git проверяются на отсутствие корпуса, изображений, отчётов и весов;
9. сетевые вызовы inference запрещены после локального получения и фиксации весов.

Свидетельство Gate 4 фиксирует рабочие пути без раскрытия ограниченных данных, результат проверки прав доступа, retention/cleanup-тестов и повторную проверку состава поставки. В локальном MVP доступ контролируется доступом к учётной записи и файловому каталогу машины; продуктовая авторизация не добавляется.

### Постепенное накопление выборки

Недостаток примеров не останавливает функциональную разработку. Система накапливает подтверждённую разметку и показывает прогресс по классам.

Технические преобразования исходного фото — кадрирование, сжатие, поворот, изменение размера или яркости — применяются для engineering-тестов. Они не считаются независимыми реальными примерами качества.

Примеры из одной товарной или связанной группы не могут попасть в разные части evaluation-набора.

### Calibration и закрытая проверка

После накопления 300 подтверждённых примеров «Накладных ногтей» набор делится по товарным группам:

- calibration: 120 примеров, по 40 `TRUE SAME`, `TRUE NEW` и `TRUE VARIANT`;
- test: 180 закрытых примеров, по 60 каждого класса.

На calibration исполнитель выбирает модель, препроцессинг и пороги. Затем он фиксирует конфигурацию и не меняет её по результатам закрытой проверки.

Это деление — ратифицированное направление плана, но оно меняет действующий метод приёмки: текущие `ART-08` и `ART-09` требуют считать метрики на всех 300 примерах. Поэтому до начала calibration нужен отдельный `FULL`-цикл поправки этих двух артефактов с независимым review и owner gate. Без утверждённой поправки результаты 180 test-примеров не дают технический `PASS`.

Если поправка не утверждена, применяется действующий нормативный метод: все 300 примеров остаются приёмочной выборкой, а модель, препроцессинг и пороги можно настраивать только на отдельном наборе, который в эти 300 не входит.

Закрытая часть подтверждает:

- `SAME_PRODUCT Recall@10` — не менее 57 правильных результатов из 60;
- `VARIANT Recall@10` — не менее 51 из 60;
- ложный уверенный `SAME_PRODUCT` — не более 3 из 60 истинных `NEW`;
- не менее 80% запросов завершаются за 5 секунд на зафиксированной локальной машине.

Если примеров меньше, функциональная реализация может быть готова, но качество не получает технический `PASS`. Владелец может продолжить накопление или отдельно открыть пересмотр `ART-08` и `ART-09`; план не снижает требование автоматически.

### Свидетельства gate

- автоматические unit-, интеграционные, контрактные и UI-тесты;
- утверждённая редакция метода оценки в `ART-08` и `ART-09` либо применение действующего метода на всех 300 примерах;
- версии корпуса, выборки, моделей и правил;
- результаты calibration без закрытых test-примеров;
- однократный итог закрытой проверки;
- распределение времени ответа;
- матрица применимых критериев `ART-09` со статусом `PASS / FAIL / NOT_RUN`;
- независимое read-only review доказательств.

`PASS` технической приёмки не доказывает бизнес-эффект. Его оценивают отдельно после baseline `MEAS-001`.

## 8. Что проверяет владелец на gates

| Gate | Что получает владелец | Какое решение принимает |
|---|---|---|
| 1 | Открытый локальный экран и краткий отчёт тестов | Подтверждает понятность минимального контура |
| 2 | Отчёты успешного и заблокированного импорта | Подтверждает смысл причин и безопасную реакцию |
| 3 | Кнопочную разметку, общий рейтинг и галерею ошибок | Подтверждает удобство разметки и состав моделей следующего этапа |
| 4 | Сквозной сценарий, метрики и матрицу `ART-09` | Утверждает или отклоняет технический результат MVP |

Владелец не проверяет код, Docker, SQL или математическую реализацию метрик. Это делают автоматические тесты, исполнитель и независимый reviewer.

## 9. Проверка каждого gate

Перед передачей результата владелец получает только воспроизводимые свидетельства:

1. Исполнитель проводит TDD-циклы и самопроверку.
2. Исполнитель запускает применимые тесты и фиксирует версии среды и данных.
3. Независимый reviewer проверяет код и свидетельства read-only.
4. Исполнитель исправляет замечания. Повторное review обязательно после `Critical` или `Major`.
5. Владелец проверяет наблюдаемый результат и принимает решение по gate.

Reviewer `PASS` не является owner approval. `NOT_RUN` не считается успешной проверкой.

## 10. Post-MVP дорожная карта

Следующие возможности открываются отдельными решениями только после результатов MVP:

1. заменить локальный `ImageStorage` адаптером MinIO;
2. добавить получение обновлений и передачу нового товара через Google Sheets;
3. добавить авторизацию, RBAC и многопользовательский контур;
4. хранить поисковые запросы и пользовательскую обратную связь;
5. добавить SHA-256, perceptual hash, текстовые и структурированные сигналы;
6. реализовать повторное ранжирование;
7. вынести длительные операции в worker и очередь;
8. добавить HNSW только после измеренной проблемы точного поиска;
9. определить backup/restore, промышленную наблюдаемость и эксплуатационный runbook.

Дорожная карта не является требованиями этих версий и не разрешает их реализацию заранее.

## 11. Зависимости и условия продолжения

- Docker ещё не установлен; установка относится к отдельному старту Gate 1.
- Веса моделей потребуют однократного получения из официальных источников. После этого версии и контрольные суммы фиксируются локально.
- Реальные примеры предоставляет и подтверждает владелец проекта; интерфейс минимизирует ручную работу до загрузки и кликов.
- Срок хранения и удаление загруженных query-изображений должны быть утверждены владельцем данных до работы с реальными примерами на Gate 3.
- Деление 300 примеров на 120 calibration и 180 test требует отдельной утверждённой поправки `ART-08` и `ART-09` до начала calibration.
- Правила обезличивания нужны до расширения использования данных за пределы локального ограниченного контура.
- Календарные оценки появятся после определения доступной загрузки исполнителя.
- Утверждение этого плана не означает начало реализации; старт требует отдельной команды владельца.
