## Сценарий проверки товара

Актор: `CHECK`. Цель: найти наиболее вероятные каталожные товары. Триггер: загрузка фото или добавление ракурса. Предусловие: доступна проверенная версия подготовленного каталога; все фото запроса относятся к одному товару. Постусловие: отображены кандидаты или пояснение невозможности поиска; карточки товаров не создаются и не изменяются.

| Шаг | Требуемое поведение | Основание в диалоге |
|---|---|---|
| Подготовка | Использовать все доступные фото каждого каталожного товара | «выбираем все» |
| Выделение | Создавать отдельные обрезки и эмбеддинги каждого выделенного ногтя, одинаковым способом для каталога и запроса | «строить эмбеддинг каждого ногтя отдельно» |
| Сопоставление | Учитывать несколько ногтей, в том числе разные рисунки; все ногти запроса имеют одинаковый вес | «Совпадение нескольких ногтей, с учётом разных рисунков»; «Принимаем правило одинаковый вес» |
| Полнота | Все выделенные и технически обрабатываемые ногти запроса участвуют; слабые совпадения не отбрасываются | «все найденные ногти запроса»; «Сначала делаем проще» |
| Уникальность | В одной паре фото каталожная область используется максимум один раз; копии не создаются; отсутствие пары учитывается как несовпадение | «Принимаем поведение» после обсуждения недостающего ногтя |
| Лишние области каталога | Области каталога, не нужные для покрытия запроса, сами по себе не снижают оценку | Подтверждение «все найденные ногти запроса» в ответ на соответствующее предложение |
| Ракурсы | Сравнивать пары фото отдельно; лучшая пара задаёт основную оценку товара; слабое фото не снижает её, повторы не дают бонуса количеством | «согласен» после предложения лучшего ракурса; «Принимаем поведение» для отдельных фото каталога |
| Дополнение | При добавлении фото пересчитывать общую выдачу по накопленному запросу | То же подтверждение «согласен» |
| Нет областей | Пропустить фото с пояснением; если все фото без областей — попросить другое фото, без резервного поиска | «да» после вопроса о поведении без резервного поиска |

Все строки: `OWNER_DECISION / VERIFIED` как выбранное поведение, не как реализованный результат. Факт истинного ногтя не проверяется дополнительным фильтром; обрезки не дорисовываются. Невозможность технически создать обрезку — отдельный открытый сценарий, а не скрытое разрешение исключать неудобные области.

## Уточнение выбранного поведения — 2026-10-07

Источник: ответы владельца в текущем диалоге — «2 — согласен с предложенными правилами» после таблицы из шести правил и «После моей проверки кандидатов». OWNER_DECISION / VERIFIED как выбор, не runtime result. Владелец принял отдельную обрезку с белым фоном, участие всех технически корректных областей, пары без повторного использования, объединение оценок трёх моделей и вкладов ногтей со значением ноль для отсутствующей пары, лучшую пару ракурсов без бонуса количества, различение отсутствия ногтей и технической ошибки. Детали реализации и поля находятся в HLD/LLD; полного утверждения пакета нет.

После поиска владелец просматривает кандидатов и определяет SAME_PRODUCT или NEW. Низкая оценка, пустой индекс, NO_NAILS и model error сами по себе не означают отсутствия товара. Сходство не называется вероятностью. Технический отказ не публикует частичный новый результат; выбранное различение исходов не утверждает все предложенные DB/evidence/UI поля.

Открыты доступность каталожных фото/покрытие, точные технические limits и принятие остальных контрактов из [ART-10](10-open-items.md). Существующие upload ограничения сохраняются.
