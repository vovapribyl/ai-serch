# План-контракт: план реализации локального MVP

## Цель

Подготовить исполнимый план разработки локального MVP через Test-Driven Development (TDD) до технического `PASS` по `ART-09`. План должен сохранить путь к развитию исторической архитектуры, но не включать функции следующих MVP.

## Входы и границы

Нормативные входы: утверждённые [`ART-06`](../06-user-scenarios-and-functional-requirements.md)–[`ART-10`](../10-risks-assumptions-and-open-questions.md). Исторические [`docs/architecture.md`](../../architecture.md) и [`docs/project-plan.md`](../../project-plan.md) используются только как источники технических гипотез.

Ратифицированные владельцем решения для плана:

- подробный маршрут охватывает текущий MVP до технического `PASS`; post-MVP показывается только дорожной картой;
- PostgreSQL с `pgvector` работает через Docker Compose, а FastAPI, тесты и локальные модели — в управляемом Python 3.12;
- интерфейс MVP работает локально на компьютере через Jinja2/HTMX;
- изображения хранятся в локальной файловой системе за интерфейсом `ImageStorage`;
- пилот сравнивает локальные OpenCLIP, DINOv2 и SigLIP2;
- сторонний репозиторий используется только как референс, без переноса кода;
- реализация делится на четыре owner gates;
- помощник разметки не требует ручного ввода: пользователь загружает фотографию и выбирает кнопки;
- примеры накапливаются постепенно; нехватка выборки не блокирует разработку, но блокирует доказанный технический `PASS` качества;
- официальные 300 примеров делятся на 120 calibration и 180 закрытых test-примеров;
- выбранное деление не считается действующим методом приёмки до отдельной утверждённой поправки `ART-08` и `ART-09`; без неё метрики считаются на всех 300 примерах;
- утверждение плана не разрешает начать установку окружения или разработку.

## Ожидаемый результат

Новый файл `docs/mvp-implementation-plan.md` содержит:

- техническую границу MVP и post-MVP;
- TDD-правила и уровни проверки;
- четыре последовательных gate с зависимостями, результатами и свидетельствами;
- упрощённый процесс накопления и разметки примеров;
- правила calibration и закрытой проверки;
- условия остановки, продолжения и отдельного начала реализации.

План не изменяет утверждённые требования, не объявляет модель выбранной и не утверждает начало реализации. Ратифицированное направление, которое расходится с действующим методом приёмки, оформляется как заблокированное до отдельной нормативной поправки.

## Самопроверка

- план не возвращает `ANALOG`, роли, запись в Google Sheets или другие исключённые функции;
- технические решения не представлены как уже реализованные или проверенные;
- TDD программного поведения отделён от ML-evaluation;
- для каждого gate указаны результат, проверка и понятное владельцу свидетельство;
- базовые меры ограниченного контура, включая проверку прав рабочего каталога, включаются до первой проверки реального `SRC-045`;
- после решения владельца политика хранения и удаления сохранённых query-фото реализуется и проверяется до их загрузки;
- нехватка реальных примеров не превращается в успешную приёмку;
- деление `120/180` не выдаётся за выполнение текущего критерия на всех 300 примерах;
- локальные ссылки, Markdown и `git diff --check` проходят проверку;
- независимый reviewer работает read-only и проверяет план до owner gate.
