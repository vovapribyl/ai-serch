# План-контракт разработки `ART-06` v0.2

> [`ART-06`](../06-user-scenarios-and-functional-requirements.md) · [Контракт `ART-06`](../artifact-contracts.md#art-06--пользовательские-сценарии-и-функциональные-требования) · [`ART-04`](../04-to-be.md) · [`ART-05`](../05-business-rules.md) · [Governance](../governance.md)

## Статус плана

- Режим работы: `FULL`.
- Статус: `RATIFIED`; выполнение начато по явному указанию владельца.
- Подтверждение: ответ владельца «Подтверждаю план» в текущей беседе от 2026-08-26.
- Состояние выполнения: `REVIEW_COMPLETED`; повторное review — `PASS`, 0/0/0.
- Следующее действие: отдельное утверждение владельца.

Исполнитель выполнил согласованные изменения `ART-06`, правил идентификации, реестров, статусов и маршрутизирующих документов. Первичное review описано в [отчёте](06-user-scenarios-and-functional-requirements-v0.2-review.md); повторная проверка обязательна из-за `Major`.

## Цель и результат

Цель — преобразовать `ART-06` v0.1 `DRAFT_STUB` в полноценный нормативный документ пользовательских сценариев и функциональных требований.

Результат должен быть понятен сотруднику компании, менеджеру ассортимента, руководителю ассортимента и владельцу проекта в административном сценарии. Документ должен связывать наблюдаемое поведение продукта с утверждённым процессом `ART-04` и бизнес-правилами `ART-05`, не дублируя их содержание.

## Согласованная граница

В `ART-06` войдут шесть атомарных сценариев:

1. поиск товара;
2. передача результата `NEW` на рассмотрение;
3. изменение категории;
4. изменение жизненного статуса;
5. управление ролями;
6. просмотр карточки и истории.

Для каждого сценария нужно определить актора, цель, триггер, предусловия, основной и альтернативные потоки, ошибки, постусловия и наблюдаемое поведение продукта.

В этап не входят интерфейс, API, архитектура, физическая модель данных, нефункциональные требования, готовые тест-кейсы и новые правила сопоставления категорий.

## Решения владельца для разработки

### Проверка фотографии

Перед поиском продукт выполняет только техническую проверку: пользователь передал хотя бы один файл, который продукт может распознать как изображение. Форматы, размеры и другие технические ограничения относятся к последующим требованиям к данным.

Если содержимого фотографии недостаточно для уверенного результата, продукт возвращает `UNCERTAIN`. Он не отклоняет такую фотографию как ошибочный вход только из-за ракурса, резкости, освещения или видимости деталей.

### Повтор после `UNCERTAIN`

Продукт не ограничивает число повторных попыток в MVP. Пользователь может передать другую или дополнительную фотографию и повторить поиск либо завершить сценарий.

Если пользователь завершает неразрешённый сценарий, продукт не создаёт карточку и не сохраняет запрос или товар.

### Конфликтующая история

Продукт показывает все обнаруженные конфликтующие записи и явно обозначает конфликт. Он не объединяет записи и не выбирает одну из них автоматически.

Руководитель разрешает конфликт через уже разрешённое изменение категории или жизненного статуса. Отдельный процесс разрешения конфликтов в этот этап не входит.

### Идентификаторы

Для сценариев вводится пространство `UC-###`, для функциональных требований — `FR-###`. Во время выполнения исполнитель должен нормативно добавить оба пространства в правила идентификации и использовать их для последующей связи с реализацией, тестированием и приёмкой.

## План выполнения

1. Записать подтверждённый пакет решений владельца в следующий доступный `SRC-*` и оформить соответствующие `DEC-*` без расширения смысла ответов.
2. Добавить пространства `UC-*` и `FR-*` в нормативные правила идентификации.
3. Подготовить `ART-06` v0.2: описать акторов, шесть сценариев, альтернативные ветки, ошибки, постусловия и атомарные функциональные требования.
4. Построить трассировку `UC → FR → правило ART-05 → последующий артефакт`. Не копировать обоснования и бизнес-правила в `ART-06`.
5. Синхронизировать текущий контекст, индексы, статусы, реестр пробелов и историю.
6. Провести авторскую самопроверку и передать пакет одному независимому read-only reviewer.
7. Исправить замечания. После `Critical` или `Major` провести повторное review.
8. Передать проверенный `ART-06` на отдельное утверждение владельца.

## Проверка результата

- Каждый сценарий соответствует `ART-04`, `ART-05` и нормативному контракту `ART-06`.
- Каждое `FR-*` связано минимум с одним `UC-*` и каноническим бизнес-правилом.
- Неизвестные технические параметры и правила других категорий не представлены как принятые требования.
- Локальные ссылки, Markdown-таблицы, новые и действующие ID, конфликтные маркеры и пробельные ошибки проверены.
- `git diff --check` не сообщает об ошибках в изменённом пакете.
- Независимый reviewer зафиксировал результат и замечания; отдельный owner gate остаётся обязательным.

Существующие несвязанные изменения рабочего каталога не входят в план и должны остаться нетронутыми.
