## 1. Назначение

Реестр определяет, какие материалы допустимо использовать при создании аналитических артефактов, какой статус имеют содержащиеся в них утверждения и какие решения уже приняты владельцем проекта.

Реестр сам по себе не является спецификацией продукта. Он нужен, чтобы:

- не выдавать гипотезы за факты;
- отличать слова заказчика от решений владельца проекта;
- не наследовать автоматически положения из прежних черновиков;
- сохранять происхождение требований;
- явно фиксировать пробелы и противоречия;
- обеспечить трассировку следующих артефактов.

## 2. Правила работы с утверждениями

### 2.1. Иерархия источников

При создании следующих аналитических артефактов применяется согласованная иерархия:

1. Явно утверждённые решения владельца проекта.
2. Позиции заказчика из интервью.
3. Наблюдаемый AS-IS из таблицы и других фактических артефактов.
4. Существующие проектные документы как проверяемые черновики.

Более высокий уровень не переписывает содержание нижнего задним числом. Например, решение владельца может изменить целевую границу проекта, но не меняет того, что заказчик сообщил о текущем процессе.

### 2.2. Классификация утверждений и доказательств

Тип утверждения и степень его подтверждения фиксируются раздельно.

| `assertion_type` | Когда используется |
|---|---|
| `FACT_CLAIM` | Проверяемое утверждение о предметной области или текущем состоянии |
| `OBSERVATION` | Результат воспроизводимой проверки таблицы, файла или процесса |
| `STAKEHOLDER_STATEMENT` | Позиция участника, зафиксированная в интервью |
| `OWNER_DECISION` | Нормативный выбор владельца проекта |
| `DRAFT_HYPOTHESIS` | Положение из старого черновика или рабочее предположение |

| `evidence_status` | Значение |
|---|---|
| `VERIFIED` | Утверждение подтверждено доступным первичным источником с точным локатором |
| `PARTIAL` | Подтверждена только часть утверждения или источник имеет существенные ограничения |
| `UNVERIFIED` | Утверждение записано, но доступного подтверждения нет |
| `CONFLICTED` | Доступные источники дают несовместимые версии |
| `NOT_AVAILABLE` | Источник недоступен для проверки |

Для незакрытых вопросов используются отдельные маркеры:

| Маркер | Значение |
|---|---|
| `UNKNOWN` | Ответ не установлен доступными источниками |
| `HUMAN_STATEMENT_UNRECORDED` | Человек сообщил ответ, но он ещё не закреплён проверяемым источником или решением |
| `DECISION_REQUIRED` | Требуется выбор владельца проекта, а не поиск факта |

Если для утверждения нет достаточного основания, оно не формулируется как факт или требование.

### 2.3. Правила трассировки

- Читаемость аналитического документа человеком имеет приоритет над максимальным количеством идентификаторов. Трассировка сохраняет происхождение и состояние значимых сущностей, но не превращает каждую строку или утверждение в отдельный реестровый объект.
- Новый ID создаётся только для объекта, который используется в нескольких артефактах либо независимо изменяется и отслеживается между редакциями по статусу, владельцу, версии, проверке или критерию приёмки. Само наличие соответствующей колонки в локальной таблице не является основанием для ID.
- По умолчанию используются `ART-*` для утверждаемых артефактов, `DEC-*` для решений владельца, `SRC-*` для источников и `GAP-*` для значимых междокументных пробелов и открытых вопросов.
- Все остальные уже существующие пространства ID имеют режим legacy/read-only: наличие `FACT-*`, `USR-*`, `ASIS-*` или другого небазового префикса не разрешает создавать в нём новые ID. Любой новый ID вне `ART-*`/`DEC-*`/`SRC-*`/`GAP-*` требует объяснения назначения и согласования владельцем независимо от того, встречался ли префикс раньше.
- Идентификаторы требований и критериев приёмки вводятся только при реальной связи с реализацией, тестом или приёмкой и после согласования соответствующего пространства владельцем.
- Локальные строки таблиц, цели, принципы, роли, участники, элементы scope, результаты, риски, ограничения, допущения и вопросы не получают отдельный ID, если не требуют самостоятельного отслеживания. Для них используются содержательные названия, заголовки и ссылки на файл или раздел.
- Для значимого фактического утверждения, бизнес-требования или бизнес-правила по-прежнему фиксируются применимые `assertion_type`, `evidence_status` и происхождение, но это не требует отдельного ID для каждого утверждения. Ссылка на основание включает `SRC-*` или `DEC-*`, достаточный локатор внутри источника, дату или версию источника и пояснение способа вывода, если утверждение не является прямым наблюдением.
- Трассировка источников размещается компактно в колонке, сноске или приложении и не должна перегружать основной текст повторяющимися кодами.
- Идентификаторы утверждённых артефактов не удаляются и не перенумеровываются без утверждённой таблицы соответствия. Локальные ID неутверждённого `DRAFT`/`REWORK` можно вывести из употребления при полной переработке без таблицы соответствия, только если на них нет нормативных ссылок из утверждённых артефактов; удаление фиксируется в истории версии и отчёте проверки. Настоящее правило применяется к новым и содержательно перерабатываемым артефактам и не требует массовой редакции уже утверждённых `ART-01` и `ART-02`.
- Для файлов локатором служат раздел, строка, запись или диапазон; для таблицы — вкладка и диапазон; для интервью — смысловой фрагмент; для решения — идентификатор пакета решения и формулировка подтверждения.
- `OWNER_DECISION` подтверждает нормативный выбор, но не может быть единственным доказательством наблюдаемого AS-IS-факта.
- Производный черновик не может быть единственным подтверждением нового факта.
- При конфликте источников фиксируются обе версии, влияние конфликта и вопрос владельцу.
- Локальные исходные файлы идентифицируются контрольной суммой SHA-256.
- Изменение файла образует новую версию источника и требует новой контрольной суммы.
- Статус `DRAFT` не делает документ нормативным.
- Только решение владельца переводит аналитический артефакт в `APPROVED_BY_OWNER`.
