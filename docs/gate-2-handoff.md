> [План завершения Gate 2](gate-2-completion-plan.md) · Актуально на 2026-09-01. Этот файл фиксирует технический результат и не является owner approval.

## Текущий статус

Прежний Gate 2 безопасной перезагрузки остановлен решением владельца `SRC-052` / `DEC-059`. В MVP один раз загружают рабочую производную копию `SRC-054` и далее работают только с этим корпусом. Поправка scope утверждена владельцем (`SRC-053`); Gate 3 до первоначальной загрузки и отдельного owner gate результата не начинается.

Техническая реализация сохранена коммитом `eb8bcd6 feat: make Gate 2 imports recoverable` в ветке `codex/gate-2-import-reliability`; ветка опубликована в `origin`. Ветка `main` не менялась.

## Что уже реализовано сверх сокращённой границы

Механизм ниже создан до решения `DEC-059`. Он может остаться в коде, но его дальнейшее развитие и дополнительные проверки перезагрузки не требуются для MVP.

- Миграция `0004_import_operations` добавляет устойчивый журнал `import_operations`.
- Импорт сначала фиксирует `operation_id` в журнале. Если это не удалось, команда завершает работу с кодом `4` и не начинает staging.
- Активация сохраняет связь версии корпуса с операцией в одной транзакции. При потерянном подтверждении после `COMMIT` сервис сверяет журнал и не удаляет уже активный корпус.
- Staging, обычный импорт и reconciliation используют общую файловую блокировку. PostgreSQL использует транзакционную advisory-блокировку при активации.
- Очистка удаляет каталоги неактивных версий до удаления их записей из БД. Невыполненная очистка остаётся повторяемой и даёт `CLEANUP_PENDING`.
- JSON-отчёт хранится по постоянному пути `reports/<operation_id>.json`. Его полезная нагрузка есть в журнале, поэтому отчёт можно восстановить после сбоя записи.
- Добавлена команда `scripts/reconcile_imports.py` для одной операции или всех незавершённых операций.

## Новая граница и следующий шаг

Реальные строки XLSX, изображения, JSON-отчёты и веса моделей в Git не добавлялись. Защищённая проверка подтвердила структуру рабочего `SRC-045`, но корпус в БД ещё не создавался.

Следующий шаг — утвердить сокращённую границу, затем один раз загрузить `SRC-045`, сохранить только агрегированное свидетельство и проверить чтение корпуса. Результат загрузки отдельно предъявляется владельцу на owner gate Gate 2; только после его явного утверждения можно переходить к Gate 3. Функцию плановой перезагрузки не развивать; решение о merge существующего технического запаса принимается отдельно.

Для проверки затем использовался отдельный Compose-проект и отдельный том. Перед следующим запуском основного локального контура стоит проверить его обычный env-файл и параметры `ai-database-1`.
