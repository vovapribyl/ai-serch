## Главная проблема: неопределённый COMMIT

PostgreSQL может успешно зафиксировать транзакцию, но приложение не получить подтверждение из-за сбоя соединения. В таком случае нельзя объявлять импорт неуспешным и удалять каталог новой версии.

Текущая частичная защита: для операции создаётся `operation_id`; после ошибки код проверяет, стала ли эта операция активной в БД. Если стала — импорт должен считаться успешным. Последняя правка также запускает cleanup после такой reconciliation-ветки.

Нужно завершить и проверить TDD:

1. Инъекционный тест: COMMIT фактически успешен, но вызывающая сторона получает ошибку.
2. Проверить, что активный новый корпус и его файлы сохраняются.
3. Проверить, что отчёт фиксирует успех или `CLEANUP_PENDING`, но не `ACTIVATION_FAILED`.

## Проблема cleanup

Старые версии должны удаляться только после успешной активации новой. При ошибке удаления файлы и DB-записи старой неактивной версии нельзя терять: следующий запуск обязан повторить cleanup.

Текущая частичная реализация хранит неактивные версии до `_cleanup_inactive_versions`; отсутствующий каталог считается уже очищенным. Есть unit-тест, где первый `rmtree` падает, новая версия остаётся активной, а следующая загрузка завершает очистку.

Осталось:

1. Не подавлять ошибки удаления staging/final-каталогов через `ignore_errors=True` без отдельной записи состояния.
2. Добавить тесты rollback после `shutil.move`, ошибки cleanup staging и частичного удаления нескольких каталогов.
3. Добавить отдельную повторную cleanup-операцию либо доказать тестом, что следующий импорт корректно повторяет очистку.

## Проблема JSON-отчёта

Отчёт пишется через временный `.tmp` и `os.replace`, поэтому публикация одного файла атомарна. Но сейчас окончательный JSON создаётся после активации корпуса. Если `write_text` или `os.replace` не сработает, активный корпус останется без итогового отчёта.

Нужно:

1. Зафиксировать операцию до активации либо хранить в БД достаточное состояние для повторной генерации отчёта.
2. Удалять временный `.tmp` при ошибке записи.
3. Добавить failure-тесты `write_text` и `os.replace`.
4. Убедиться, что все error-ветки передают `rejected_rows`.

Текущий отчёт уже содержит: `accepted_rows`, `rejected_rows_count`, счётчики причин, список `{source_row, reason}`, дубликаты, `corpus_replaced`, `critical_error`.

## Остаток обязательных тестов

- ошибка после переноса staging-файлов;
- успешный COMMIT с потерянным ответом;
- частичный cleanup и повтор;
- ошибка удаления staging;
- сбой `write_text` и `os.replace` отчёта;
- ненулевой CLI exit code для обычной ошибки и `CLEANUP_PENDING`;
- сериализация параллельных импортов;
- PostgreSQL integration: миграции с нуля, успешная замена, критическая ошибка сохраняет старый активный корпус.
