# Инструкции для работы с проектом

## Быстрый старт новой сессии

Сначала прочитай только:

1. [`docs/analysis/current-context.md`](docs/analysis/current-context.md) — текущая точка продолжения и принятые инварианты.
2. [`docs/analysis/README.md`](docs/analysis/README.md) — карта артефактов и маршруты чтения.

Затем открывай документы выборочно:

- решения, источники, пробелы или статусы — `docs/analysis/00-source-and-decision-register.md`;
- границы и цели продукта — `docs/analysis/01-vision-and-scope.md`;
- отчёт критика — соответствующий файл в `docs/analysis/reviews/`;
- исходные наблюдения — только источник, на который ссылается `ART-00`.

Не загружай целиком `docs/architecture.md`, `docs/project-plan.md` и `docs/discovery/*`, если задача прямо не требует исторической или технической гипотезы. Эти документы созданы раньше утверждённого аналитического пакета и не являются нормативными.

## Приоритет источников

При конфликте используй следующий порядок:

1. последние утверждённые решения в `ART-00`;
2. последний утверждённый предметный артефакт;
3. первичные источники с указанным локатором;
4. исторические черновики только как источник гипотез.

Не превращай `UNKNOWN`, предложение модели или техническую осуществимость в подтверждённый факт либо бизнес-решение.

## Режимы создания и проверки аналитических документов

Для нового, сложного артефакта или содержательного изменения применяется полный маршрут:

1. Исполнитель сам составляет короткий план-контракт: цель и границы, нормативные входы, запрещённые выводы, ожидаемый результат и критерии самопроверки.
2. Тот же исполнитель создаёт или изменяет документ и проводит самопроверку.
3. Независимый ревьюер выполняет read-only проверку и не редактирует артефакт.
4. Исполнитель исправляет замечания. Повторное независимое ревью обязательно только после замечания уровня `Critical` или `Major`.
5. Владелец проекта явно утверждает результат до перехода к следующему зависимому артефакту.
6. После закрытия gate обновляются `ART-00`, `docs/analysis/README.md`, `docs/analysis/current-context.md` и `docs/project-status.md`.

В полном маршруте используются только две агентные роли: исполнитель и независимый ревьюер. Отдельный агент-планировщик не создаётся; планирование является обязанностью исполнителя. Владелец проекта остаётся человеком, который утверждает результат, а не дополнительной агентной ролью.

Полный маршрут применяй также к правке, если она меняет `OWNER_DECISION`, scope, определения, требования, статус доказательств или gate/status, либо если её смысл неоднозначен.

Для мелкой ясной правки, которая не затрагивает эти элементы, действует облегчённый маршрут: исполнитель вносит изменение и проводит самопроверку; отдельный ревьюер не обязателен. Отдельный планировщик не используется и в этом маршруте.

## Оформление и общение

- Основной язык — русский; идентификаторы — английские.
- Для процессов допустим Mermaid flowchart.
- Несколько вопросов задавай одним пакетом: **вопрос → влияние → предполагаемый ответ модели**.
- Ссылки между локальными Markdown-файлами делай относительными.
- Не публикуй исходные данные и полный идентификатор Google Sheets: действует `RESTRICTED_PENDING_CLASSIFICATION`.
- После правок проверяй ссылки, структуру Markdown-таблиц, ссылки на действующие `SRC-*`/`DEC-*`/`GAP-*`, ссылки на уже существующие legacy-ID вроде `FACT-*` и отсутствие конфликтных маркеров.

## Человекоориентированная трассировка

- Читаемость аналитических документов человеком имеет приоритет над максимальным количеством идентификаторов.
- Новый ID создавай только для объекта, который используется в нескольких артефактах либо независимо изменяется и отслеживается между редакциями по статусу, владельцу, версии, проверке или критерию приёмки. Само наличие соответствующей колонки в локальной таблице не является основанием для ID.
- По умолчанию допустимы только `ART-*` для утверждаемых артефактов, `DEC-*` для решений владельца, `SRC-*` для источников и `GAP-*` для значимых междокументных пробелов и открытых вопросов.
- Все остальные уже существующие пространства ID являются legacy/read-only: их наличие не разрешает создавать в них новые ID. Любой новый ID вне `ART-*`/`DEC-*`/`SRC-*`/`GAP-*` требует объяснения назначения и согласования владельцем, даже если такой префикс уже встречается в проекте.
- Идентификаторы требований и критериев приёмки вводи только при реальной связи с реализацией, тестом или приёмкой и после согласования соответствующего пространства владельцем.
- Не создавай отдельные ID для локальных строк таблиц, целей, принципов, ролей, участников, элементов scope, результатов, рисков, ограничений, допущений и вопросов, если они не требуют самостоятельного отслеживания.
- Для обычной навигации используй содержательные заголовки, названия терминов и ссылки на файл или раздел. Трассировку источников размещай компактно в колонке, сноске или приложении, не перегружая основной текст.
- Не удаляй и не перенумеровывай ID утверждённых артефактов без утверждённой таблицы соответствия. Локальные ID неутверждённого `DRAFT`/`REWORK` можно вывести из употребления при полной переработке без таблицы соответствия, только если на них нет нормативных ссылок из утверждённых артефактов; такое удаление фиксируется в истории версии и отчёте проверки.
