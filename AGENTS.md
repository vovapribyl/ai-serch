# Инструкции для работы с проектом

## Маршрут задачи

Сначала классифицируй запрос; подробные критерии находятся в [`docs/analysis/governance.md`](docs/analysis/governance.md).

- `FAST_PATH`: опечатка, локальное переименование без изменения смысла, ссылка или форматирование. Читай только целевой файл и точные ссылки; не открывай `current-context.md`, `README.md` или `ART-00` без предметной зависимости. Не создавай план-контракт, субагента и записи в реестрах.
- `STANDARD`: ограниченный анализ или содержательная правка без изменения нормативных решений и gate. Читай только прямо относящиеся документы; отдельный ревьюер по умолчанию не нужен.
- `FULL`: новый сложный артефакт либо изменение `OWNER_DECISION`, scope, определений, требований, evidence status или gate/status. Сначала прочитай [`current-context.md`](docs/analysis/current-context.md), затем только нужные реестры и артефакты по [`docs/analysis/README.md`](docs/analysis/README.md).

Наличие слова «документ» само по себе не переводит задачу в `FULL`.

## Модели

| Режим | Рекомендуемая модель | Reasoning |
|---|---|---|
| `FAST_PATH` | `gpt-5.6-luna` | `low` |
| `STANDARD` | `gpt-5.6-terra` | `medium` |
| `FULL` и независимый ревьюер | `gpt-5.6-sol` | `high` |

Явный выбор пользователя имеет приоритет и не блокирует работу. Актуальность матрицы проверяй по официальной документации перед её изменением, а не перед каждой задачей.

## Полный маршрут

1. Исполнитель сам составляет короткий план-контракт, изменяет документ и проводит самопроверку.
2. Один независимый ревьюер проверяет read-only и не редактирует файлы.
3. Исполнитель исправляет замечания; повторное ревью обязательно только после `Critical` или `Major`.
4. Владелец явно утверждает нормативный результат до следующего зависимого артефакта.

Отдельные агенты-планировщик и автор запрещены. Для `FAST_PATH` и обычного `STANDARD` отдельный ревьюер не создаётся.

## Источники и безопасность

Иерархия источников и статусы доказательств определены только в [`governance.md`, §4](docs/analysis/governance.md#4-источники-и-доказательность). Не превращай `UNKNOWN`, предложение модели или техническую осуществимость в факт или бизнес-решение.

Не загружай целиком крупный CSV, таблицу, лог, `docs/architecture.md`, `docs/project-plan.md` или `docs/discovery/*`, если задача решается схемой, точным диапазоном или агрегатом. Не публикуй исходные данные и полный идентификатор Google Sheets: действует `RESTRICTED_PENDING_CLASSIFICATION`.

## Границы аналитических артефактов

Перед созданием или содержательной правкой `ART-*` проверь его нормативный контракт в [`docs/analysis/artifact-contracts.md`](docs/analysis/artifact-contracts.md). Не смешивай бизнес-требования, бизнес-правила, функциональные требования, данные, NFR и критерии приёмки.

Материал вне контракта переноси в канонический целевой артефакт с сохранением смысла, источника и статуса. Удаляй исходный подробный фрагмент только после записи и проверки целевого. Если целевого файла нет, создай минимальный `DRAFT_STUB`; он не считается готовым артефактом или разрешением начать зависимую работу.

## Оформление и проверка

- Документы — на русском, идентификаторы — на английском; процессы можно показывать Mermaid flowchart.
- Для визуально значимых диаграмм используй локальный навык [`diagram-design`](.codex/skills/diagram-design/SKILL.md): по умолчанию выбирай минималистичный вариант (светлый фон, тонкие линии, один акцент). Ориентир — 4–8 сущностей на одном уровне детализации, но не лимит: при большей сложности группируй или декомпозируй схему. Полноформатный HTML/SVG создавай только по явному запросу либо когда это оправдано портфолио.
- Несколько вопросов задавай пакетом: **вопрос → влияние → предполагаемый ответ модели**.
- Локальные Markdown-ссылки делай относительными.
- Новые ID по умолчанию допустимы только в `ART-*`, `DEC-*`, `SRC-*`, `GAP-*`; остальные пространства legacy/read-only.
- Проверка пропорциональна режиму: для `FAST_PATH` — точный поиск и diff; для `STANDARD/FULL` — релевантные ссылки, таблицы, ID, конфликтные маркеры и `git diff --check`.
